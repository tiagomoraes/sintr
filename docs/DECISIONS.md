# Decisions and trade-offs

Short records of choices made while building, with the reason, so they can be revisited deliberately. Newest last.

## F0 foundation

1. **Sensitive columns are declared once.** `SEALED` in `packages/core/src/db/sealed.ts` lists every sealed column. Repositories seal and open through it, the associated data of each value names its `table.column`, and a schema test fails if a `bytea` column is neither sealed content nor key material. One column per field (not one JSON blob per row) keeps partial updates simple and makes the sensitive surface visible in the schema.

2. **Clear metadata, sealed words.** Dates, the 0 to 100 and 0 to 5 scales, sleep hours, kinds and statuses stay in the clear so they can be aggregated without decrypting; every free-text field is sealed (PRODUCT.md, Risks). `entries.peak_intensity` is derived from the sealed emotions and stored clear for the same reason.

3. **Field AAD is column plus owner, not row.** Binding to the row id would need ids generated before INSERT; column plus owner already stops a ciphertext from being moved to another field or another person.

4. **Two exceptions to "every table has `user_id`".** `users` (its id is the scope) and `verification_tokens` (Better Auth creates them before a user exists; they hold no ledger content). The schema test names both.

5. **Subscriptions and usage counters are not in the schema yet.** They belong to billing (F4); migrations are versioned, so adding them then costs nothing now.

6. **Consent at sign-up, enforced on the server.** A Better Auth `before` hook refuses sign-up without the consent flag, and the after-create hook records it. If that record were ever missing, or the wording version changes, the shell sends the person to `/consent` before anything opens.

7. **No email in F0.** Magic link, email verification and password reset need an email transport, which arrives with the report send (F2). Rather than log links (forbidden) or half-enable them, those Better Auth routes are disabled. Consequence: sign-up still reveals that an email is registered, and a forgotten password cannot be reset yet.

8. **"Rotating sessions" means sliding sessions plus a new token per sign-in.** Better Auth 1.7 extends a used session after `updateAge` but does not rotate the token value in place. Cookie caching is off so revocation is immediate.

9. **Middleware sets headers only.** An optimistic redirect in middleware was removed: Next reports the host as `localhost` there, which moved browsers to another origin and failed Better Auth's origin check. Each page checks the session on the server instead; that check is the gate either way, and its redirect is relative.

10. **Every page renders per request.** Required for the nonce-based CSP; the app is almost entirely authenticated pages, so nothing is lost.

11. **The worker has no auth.** The core runtime is split into a base (repositories, maintenance) and the web runtime (base plus Better Auth), so the worker bundle carries neither Better Auth nor the native Argon2 module.

12. **One image for app, worker and migrations.** The Next.js standalone server, plus esbuild bundles of the worker and the migration runner. `SINTR_STANDALONE=1` turns on standalone output only in the Docker build, so local builds use `next start` without warnings.

13. **Dev Postgres on Docker's default bridge.** The dev database does not create a network, so it starts even where a VPN has exhausted Docker's address pools. The self-host stack needs its own network; `SINTR_DOCKER_SUBNET` gives it an explicit subnet on such hosts, through an override file applied only when set.

14. **Same port for dev and self-host.** Both serve `http://localhost:3000`, so one `.env` (and one `SINTR_URL`) works for either; they cannot run at the same time.

15. **`.env` is generated by POSIX sh.** Self-hosting needs Docker and `make`, not Node.

16. **Versions held back.** TypeScript 5.9 and ESLint 9, because typescript-eslint and the Next lint plugin do not support TypeScript 7 or ESLint 10 yet. Next.js stays on 15 as the brief asks.

17. **English only for now.** The app copy is English; i18n (the site has eight languages) comes later. The person's own words are stored and shown as written, in any language.

## F1 capture

18. **Where the assistant's key lives, and how it is encrypted.** In `agent_settings.api_key`, one row per person, next to the provider, base URL and model (those three in the clear: they name a service, not the person). The key is sealed exactly like ledger content: AES-256-GCM with the person's own data key, bound to `agent_settings.api_key` and the person's id as associated data, so a dump shows an envelope and a key copied to another account fails to open. The settings screen gets `agentSettings.get()`, which reduces the key to its last four characters (and only for keys of 16 characters or more); the key itself comes out only through `credentials()`, on the server, for the call to the provider. It is never sent to the browser, never logged, and saving or removing it is an audit event without the key. A saved key belongs to the provider and address it was saved for: changing either removes it (in the repository, whoever calls it), so it is never sent to another service. A test writes a key and scans the stored row and a text dump of the database for it, and the end-to-end suite checks the page and its data.

19. **Keys and base URLs are always passed to the provider explicitly.** The Anthropic and Google providers of the AI SDK fall back to `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` and `GOOGLE_GENERATIVE_AI_API_KEY` when nothing is given, which would spend an operator's key on another person's conversation. sintr always gives both (the default base URLs are written in the code), and a test sets those variables and checks they are not used.

20. **Three provider kinds.** An OpenAI-compatible endpoint (base URL, optional key, model) covers OpenAI, OpenRouter, Ollama, LiteLLM, vLLM and most gateways; Anthropic and Google are named. Self-host may point anywhere over http or https, including a model on the same machine (`host.docker.internal` in the self-host stack). SaaS mode accepts only https to a public host name (a trailing dot does not get past the check) and refuses redirects, so a public host cannot bounce a call to an internal address; resolving names to stop DNS tricks is F4 hardening.

21. **A draft is not a record.** The assistant's tools can only propose: a proposal (`proposals`, payload sealed) waits for the person. Confirming it creates the entry or check-in in the same transaction that marks it saved, and a proposal is decided once. The person's explicit yes is the Confirm button, an edited version saved from the card, or a message that is only an instruction to save ("salva", "pode salvar", "save it"). That message is recognised by a strict pattern in the driver, before the model runs; the model never decides that the person said yes, and "salva, mas muda a intensidade" is not a yes. Check-ins drafted in the conversation follow the same rule, so the tool the brief calls "saving a check-in" proposes one.

22. **"Never invent" is checked in code.** Before a draft is stored, its thoughts, hot thought, alternative thought and emotion names must be found in the person's own messages (forgiving case, spacing and quote styles, at word boundaries), and what is stored is the person's span, not the model's copy. Every number (intensities, believability, check-in scales, sleep) must be one the person wrote, in digits or as a small number word (words that are also articles, such as "um", "uma" and "dos", do not count). This stops invented numbers, not misplaced ones: a number written anywhere in the conversation passes for any field, and tying each number to its field is left for later. A time the model writes without an offset is read where the person is, and a bare date is refused, since its time would be invented. A refused draft goes back to the model with the reason, and nothing is kept. The situation and the evidence are allowed to be condensed, so they are not checked word for word; the prompt asks for fidelity there.

23. **The crisis protocol does not depend on a model.** Every message is screened by fixed patterns (Portuguese, English, Spanish) before any model call, after folding case, accents and curly apostrophes. A match stops the diary with a fixed, warm message in the person's language that names CVV 188 and SAMU 192, and the help lines open on screen; this works even with no provider set up. The patterns are sensitive to self-harm and narrow on violence (stated future intent only), because idioms ("morrer de vergonha", "minha mãe vai me matar") and anger told in the past are things people record (an idiom is removed without what follows it, so "morrendo de vontade de me matar" still stops); the model is told to call `signal_crisis` for anything else it notices. From then on that conversation stays paused: the model gets crisis-only instructions and no tools, its failure falls back to the fixed message, and the person can start a new conversation when ready. A conversation that opens on a crisis gets no title, so it is not listed under those words.

24. **The server is the record of a conversation.** The browser sends only the new words; the server loads the history, stores the person's message before the model runs (so a failure loses nothing) and the reply after. A reply that fails (a provider error, not a refused tool call the model can recover from) is not stored, and drafts made during it are withdrawn; a reply that stopped the diary is always stored. Only a new message can say "salva": retrying a failed reply does not. Messages are stored as their UI parts in JSON (`{ v: 1, parts }`) inside the sealed `messages.content`; plain-text rows read as one text part. The model sees the last 40 messages, with each draft's current decision written into its tool result.

25. **What reaches the provider.** The conversation's messages and, when the model asks with `recent_context`, a summary of the last seven days: dates, entry titles (or the first 120 characters of the situation), emotions with intensities, and check-in scales. Nothing else from the diary. Calls run with the AI SDK's telemetry off, and its console defaults (errors written whole by `streamText`, warnings through `process.emitWarning`) are replaced by the redacting logger.

26. **Corrections keep the original.** `entries.correct` and `checkins.correct` update the record and write a `corrections` row with the names of the changed fields (clear) and what they held before plus an optional note (sealed). A change that only fills empty fields reads as completing the record, the pack's "completed with". Fields equal to what is stored are not part of a change; the time field holds minutes only, so a time left as shown is not a change, and line endings are normalised, so a browser's CRLF is not either. A draft edited on its card is laid over the stored draft, so what the person left alone keeps the drafted value.

27. **Conversation retention.** `agent_settings.conversation_retention_days`: empty keeps conversations until the person deletes them (the default); 30, 90 or 365 days after the last message are offered. The worker purges hourly by date, reading no content; drafts go with their conversation, entries and check-ins saved from it stay.

28. **An offline assistant for tests.** `SINTR_FAKE_AGENT=1` replaces the provider call with a scripted model (`@sintr/agent/testing`), so `make test` never reaches a real model or uses a key. A provider must still be saved, the app says on screen that replies are scripted, and saas mode refuses the flag. The unit tests use the same scripted model with explicit scripts.

29. **Plain text from the model.** Replies are rendered as text, not Markdown, and em and en dashes in the model's text are rewritten as it streams (the person's words in drafts are left alone).

30. **AI SDK 7.** The current major at the time of writing; its v7 names are used (`instructions`, `toUIMessageStream`, `onEnd`, `isStepCount`). Data API routes check the `Origin` header on top of SameSite=Lax cookies.

## F2 report

31. **A report is structured JSON, not Markdown.** The pack's report is a Markdown file the agent writes and `report_pdf.py` reads leniently. In the product the model fills one tool (`write_report`) with the prose of the six sections and the choice of moments, and sintr stores the result as JSON (`{ v: 1, ... }`, sealed in `reports.content`, like messages in F1). Nothing has to guess what a model meant, the person edits it as a page rather than as a file format, and the PDF and the app read the same structure.

32. **Moments are copies of entries.** The model chooses which entries become moments and may condense what happened and what the person did; the thoughts, the strongest thought, the emotions and intensities, the evidence, the alternative thought and its believability, and the re-rate are copied from the entry when the report is prepared. The check-in notes are copied from the check-ins. The person may rewrite the prose and remove items, never a copied field (`editReport` refuses it); to change those words they change the entry, and the check then says the moment no longer matches it. Numbers are never typed: the averages, the grid and the chart are computed from the check-ins.

33. **The quote check marks instead of trusting.** Every quoted span in the prose is looked up in the diary word for word (case, spacing and quote styles forgiven, at word boundaries), in the entries and check-in notes of the four weeks up to the end of the period and in the therapy notes. The model gets a refused draft back with the reasons (also causes, clinical labels, undated observations and entries outside the period), twice at most; a draft still wrong is kept and marked, so the person sees it before approving. A quote that is not found keeps its marks but never gets the peach highlighter, in the app or the PDF, so the page's promise ("highlighted words are the person's exact words") stays true even for words the person typed in themselves.

34. **The period follows the pack, with three product rules.** A report is for a session and covers the days since the previous report ended, up to `report_lead` before the session; the first covers the 7 days before; without a session it is the calendar week, as far as it has gone (Monday, or where the previous report ended, to the moment it is prepared; preparing it again takes it further, never past Sunday), so no report claims days that have not happened. In addition: after a pause longer than four weeks, a period reaches back four weeks, not to the last report; a one-off date (`therapy_settings.next_session_at`) replaces the weekly session nearest to it (within half a week) and the weekly schedule resumes after it; and nothing is prepared for a session that already started (a worker that was down skips it, and the next report starts where the last one ended, so nothing is lost).

35. **A moved session moves the draft.** If the latest report is an untouched draft (`edited_at` empty) for a session that is no longer in the schedule, or that has not happened yet, the scheduler prepares that same report again for the new session (same start, new end, a revision kept) instead of starting a second one. A draft the person changed is never rewritten by the scheduler.

36. **Scheduling is a reconciler, not timers.** The worker runs `prepare-reports` every minute: for everyone with a session it asks the planner (`planScheduledReport`) what is due now, from the schedule as it is now. A changed setting or a restart needs no rescheduling, and two unique keys, `(user_id, period_end)` and `(user_id, session_at)` for session reports, keep a retried tick, a second worker or two tabs from keeping two reports for the same period or session. The worker prepares only for people whose latest consent to process their health data is granted and current, the same gate every page applies. A preparation abandoned by the person (a reload during "Prepare it now") keeps nothing. The scheduler takes a clock, so the tests move time by hand. "Prepare it now" runs in the request instead, because the person is waiting for it; it covers what exists so far, and the scheduler later brings that draft up to the preparation time if it is still untouched.

37. **Two yeses: approve, then send.** Approving freezes the numbers into the content and prints the final PDF (no draft mark), which is stored; it sends nothing. Sending is a second, explicit yes on that report that names the recipient: the browser sends back the address the person saw, and the server refuses if the settings changed since. The consent (`report_send`, versioned, naming the report and the recipient) and an audit event are recorded and committed first, so they stay on record whatever follows; then the email is sent with the report row locked, and the report is marked sent (recipient and time) only after the transport accepted it. A second send of the same report waits for the lock and then finds it sent, so the therapist never gets it twice; a failed send is audited and leaves it approved. Approving is refused if the draft changed (an edit, a new preparation) while its PDF was printing, so what is approved is what the person read. Any change to the words makes it a draft again; a sent report is final, and its PDF stays available. `require_approval` stays a constant, not a switch.

38. **Email is one interface and SMTP from the environment.** `EmailTransport` has four implementations: SMTP (nodemailer, `SINTR_SMTP_*` and `SINTR_EMAIL_FROM`), an outbox directory for the end-to-end tests, an in-memory fake for unit tests, and off (the default). A managed provider can be a fifth later. Transports never log and refuse a second recipient or a header in the subject. Email carries no diary content except the PDF the person approved: the notice to the person is a link and a sentence, sent only when they opted in (`report_notice_email`) and to a verified address.

39. **Password reset and email confirmation open with email.** The Better Auth routes F0 kept closed (`/request-password-reset`, `/reset-password`, `/send-verification-email`, `/verify-email`) are enabled only when a transport is available, and stay closed otherwise. A confirmation link is sent at sign-up but not required to sign in: a self-hosted diary must not lock its owner out over a mail setting. These emails are not awaited and a failed send is logged as a code, so neither the answer nor the time it takes tells who has an account. Sign-up still does (F0, decision 7); closing that needs `requireEmailVerification`, which changes sign-up and is left for F4.

40. **The PDF is HTML printed by Chromium, embedded and offline.** `reportDocument` builds one self-contained page (the sintr design system, the fonts and the window light inline, no script) and `renderPdf` prints it with playwright-core, JavaScript off and every request refused; there is nothing to fetch and nothing to run. The light is the app's own `WindowLight`, rendered once to a JPEG by `make report-assets` (blur and blend modes look different in each PDF viewer). The fonts and the light are embedded in a generated module, so the web app (which bundles `@sintr/core`) reads no files at run time; a test fails if they drift from `packages/ui/fonts`. The Docker image installs Alpine's Chromium and points `SINTR_CHROMIUM_PATH` at it; development and tests use Playwright's, which `make setup` installs. playwright-core is pinned to the same version as `@playwright/test`, so both use the one browser CI caches by that version. Chromium runs without its own sandbox, as Playwright does by default and as an unprivileged container requires; the page it prints is our own escaped HTML, offline and without script. A browser is started per print, at most two at a time per web process; a draft's preview is printed on demand, an approved report's PDF is read from storage.

41. **The report's language is the person's choice.** `profiles.language` (English, Portuguese or Spanish, chosen in Therapy) sets the report's headings and the language the assistant writes in; the person's own words are never translated. The app's copy, dates included, stays English (decision 17).

42. **Without an assistant, sintr prepares what it can.** With no provider, a provider that fails, or a model that answers without the tool, the draft holds the moments copied from the strongest entries, the check-in notes and the person's own topics, and says why the prose is empty. Nothing is made up to fill it.

## F3 connect your agent

43. **MCP is a stateless route of the web app.** `/mcp` is Streamable HTTP in stateless mode with JSON answers: every POST carries its key, runs a fresh server inside that person's scope, and leaves nothing behind (no session id to store, no event stream to hold open, `GET` and `DELETE` answer 405). One process model, the same as every other route, and nothing to clean up or leak. It sits outside `/api` (where the session cookie and the origin check rule) and outside the page middleware (CSP nonces), because the key, not a cookie, is its credential. Its limits (calls per key, each message of a batch counted, wrong keys per address, body size) are counted in memory per web process; a second process only loosens them. Only wrong keys are throttled by address, after the lookup: ChatGPT and Claude call from shared addresses, so one person's stale key must not lock out everyone else's working one.

44. **The key is the only credential, as a header or inside the address.** `Authorization: Bearer` is the normal path. ChatGPT cannot send a key of its own, and Claude's request headers are in beta for some organisations, so `/mcp/<key>` is accepted too; the address is then a secret, the route is logged as `/mcp` only, Caddy keeps no access log, and the Connect screen says so. OAuth is the standard way for remote clients and would remove the key from the address, but it is a whole authorization server (registration, consent, refresh); it is left for later. A browser on another origin is refused and no CORS headers are sent, so no web page can use a key; cookies are never read.

45. **Three kinds of access over the per-data-type scopes.** The scopes from F0 stay per data type; the app offers three sets of them ("Read and save", "Save only", "Read only", in `API_TOKEN_ACCESS`), holding only the scopes the tools use. A key lists only the tools its scopes allow, and every call checks again. "Save only" exists for a person who wants their assistant to record without ever reading the diary back.

46. **Over MCP, a save is a record, not a draft.** In Talk a draft waits for the Confirm button or a "salva" that sintr recognises itself (decision 21). Over MCP the conversation belongs to the person's assistant and sintr cannot see their yes; making them open sintr to confirm each draft would defeat the point of staying in their assistant. So the instructions require showing the draft and saving only after the yes, `save_entry` and `save_checkin` require `personConfirmed: true`, the record is held to the same checks as Talk's drafts, and the person can correct it in the app, which keeps what it said before (decision 26). The audit log records each save with the key's id.

47. **The capture rules are imported, not copied.** The checks that keep a draft in the person's words, the crisis screen and its fixed messages live in `@sintr/agent` since F1. The MCP server imports them from a light entry, `@sintr/agent/rules`, which loads no AI SDK at run time; scoping, sealing and the domain validation come from `@sintr/core`. Moving the rules into core was considered: they are capture rules, both shells now use the same functions, and a move would only rename them.

48. **The person's words travel with the save and are dropped.** The verbatim checks need the person's own messages, which only the assistant has, so it passes them in `personWords` (at most 40, each at most 20,000 characters, 1 MB per request). sintr checks the draft against them, stores the person's exact spans, and keeps nothing else of them. An assistant could pass words the person never said; the instructions forbid it, and the checks still stop paraphrase and invented numbers coming from the model's own copy.

49. **The crisis protocol over MCP.** sintr cannot interrupt another assistant's conversation. The instructions put the protocol first (stop the diary, warmth, CVV 188, SAMU 192, the local emergency number, someone they trust), and every save screens the person's words and the draft with the patterns of decision 23: on a match nothing is saved and the answer carries `"crisis": true`, the fixed message in the person's language, the lines, and the instruction to stop. It is logged as a code.

50. **Reads are small, and the report stays in the app.** `recent_context` is F1's summary (decision 25) with ids, at most 14 days; `read_entry` opens one entry; `therapy_overview` leaves out the therapist's name and address, which the assistant does not need; `prepare_report` returns the digest of the next report's period (computed exactly as the report would be, at most 40 entries) and the report's status, and changes nothing: preparing a draft would be a write under a read key and would spend the person's in-app provider. Nothing in MCP can approve or send a report.

51. **The stdio bridge forwards; it is not a second server.** Local clients run `sintr-mcp.mjs`, which forwards stdio to `/mcp` with the key from `SINTR_URL` and `SINTR_TOKEN` (or `~/.config/sintr/mcp.json`). It has no database access, so the HTTP endpoint stays the one place keys, scopes and checks are enforced. It is bundled into one file and served by the app at `/sintr-mcp.mjs`, so a person gets it from their own sintr; it refuses to send the key over plain http to another machine unless told to.

52. **"Connected" comes from the key itself.** `last_used_at` is updated on every authenticated call, and the name a client gives at `initialize` (`clientInfo.name`, letters, digits and a few marks, at most 60) is kept in `api_tokens.last_client`. The Connect screen turns "Waiting for your assistant" into "Connected" by refreshing while a new key waits, and each key says when it last talked to sintr and from which client. The name is the client's own claim, shown as text, never trusted for anything.

53. **Connect is a screen of its own.** It is in the navigation next to Settings, written for someone who has never heard of MCP: one sentence first, one button for a key (name and access optional), the key shown once, each assistant's steps with the address and key filled in, the live line, and the technical detail behind a closed disclosure. Settings lists the same keys. Each client's commands, files and menus were checked against its documentation on 2026-10-18 (`docs/MCP.md` lists the sources); what could not be checked is said on the screen instead of guessed. Keys made without a name are numbered ("My assistant 2").

## F4 the therapist

54. **One account kind; a practice is opened from inside.** There is no therapist sign-up. Any account can open one practice (a unique index on `practices.user_id`) from Settings or `/practice`, or on the way while accepting a person's invite. Someone who never opens one sees nothing new except Sharing, the person's own side; the Practice group appears in the navigation only once a practice exists. The professional's own diary is untouched by it.

55. **The link is the unit of trust, and the database holds its rules.** A link joins one person and one practice and is `pending` (a practice accepted the person's invite, the person has not confirmed), `active` or `ended`. A check refuses `active` without the person's consent and both acceptances; another refuses an ended link that still holds a key or a name; a partial unique index keeps one open link per person and practice. The ended row stays, with ids and dates only, so both audit logs keep pointing at something.

56. **Double opt-in in both directions, and the person's yes always names the practice.** A practice's invite is the practice's yes; the person sees the professional's name and details, then accepts with the consent (`practice_link`, versioned, recording the practice as shown). A person's invite to their therapist cannot carry that consent, because the person does not yet know who will accept it: the professional accepts from their practice (which holds a seat), and the person then confirms that practice by name, with the consent. A code that reaches the wrong hands can never receive anything without the person's later yes to that exact practice. "As shown" is checked: the page sends back the practice's line it displayed (name, practice, registration), and the consent is refused if the practice renamed itself in between, for the link and for each report shared from the report page.

57. **Invite codes.** Twelve characters of Crockford's base32 (60 bits), shown as `XXXX-XXXX-XXXX` to be read aloud or typed, and the link `/join/<code>`. Typing forgives case, spaces, dashes and the letters that look like digits. Codes are looked up by an HMAC keyed from the master key (HKDF), so a dump alone cannot be searched by trying every code; the code itself is kept sealed for its creator to copy again. Seven days, one use, revocable. Unknown, expired, revoked and used codes get the same page, and lookups and acceptances are limited per address (30 every 10 minutes, in memory; the address is the last one the proxy in front added, as for MCP). `/join` shows who is inviting to anyone holding the code, signed in or not: the name is what makes the link trustworthy, and the holder is who it was sent to.

58. **What travels through a link is sealed with the link's own key, and ending the link destroys it.** Each link gets a data key wrapped by the master key and bound to the link's id (`links.wrapped_key`, key material like `user_keys`). The name the person chose and every shared report (page and PDF) are sealed with it. Ending a link deletes the copies and sets the key and the name to null, which the database requires of an ended link: even a copy that survived somewhere in the live database could not be opened any more. A database backup taken before still holds the key; that is said in PRIVACY.

59. **Two openings across accounts, both of words written for that audience.** The practice's names are sealed with the professional's own key and opened for the people holding its invite or linked to it; the name a person chose for their invite is sealed with their key and opened for the professional holding the code. Nothing else of one account is ever opened for another, and both openings live in one module (`repositories/links.ts`).

60. **A shared report is a copy of what was approved, never a view into the diary.** Sharing copies the approved content (its numbers and the quotes found word for word, both frozen at approval, so the copy reads exactly as the approved PDF even if the diary changed since) and the approved PDF into `shared_reports`. The practice side has no query that reaches entries, check-ins, conversations, drafts or any report that was not shared, and none that runs through a link that is not active. Each share needs a `report_share` consent naming the report and the link; composite keys make the database refuse a share whose link, report or consent belongs to another person. A shared report's words are final, as a sent one's are.

61. **"Ask me each time" by default; "send what I approve" keeps the per-report yes.** With the second, approving is the yes for that report: the approve button names the practices ("Approve and share with Dr. ..."), the browser sends back the links it named, and the server approves nothing if they changed since. A consent is recorded for each report and practice either way. With the first, the report page offers one explicit yes per practice after approval, like an email send.

62. **Ending is one action, from either side, at once.** The person's "Stop sharing" and the professional's "Disconnect" end the link the same way: copies deleted, the link's key and name destroyed, notices about the link removed, the other side told. When the person ends an active link, a withdrawal (`granted = false`) is added to their consent log. The professional's notice says a patient ended their link, without the name: that name was the person's, given under the consent just withdrawn. A PDF already downloaded is outside sintr; the screen says so before the person stops. A practice reading a report holds a share lock on its link, so a reading in flight finishes before the end commits, and none starts after it.

63. **Audited in both accounts.** Events across a link are written to the audit log of each account concerned (the person's and the professional's), so each log is complete on its own: invites made, revoked and accepted, links activated, declined, ended and changed, consents, shares made, read and downloaded. The person also sees, on each shared report, when it was first opened.

64. **Seats, structurally, without payments.** A practice has a plan label and a seat count. A seat is taken by an active link and held by a link waiting for the person's confirmation or a practice invite not yet accepted; every seat check runs with the practice row locked. Seats come from the installation (`SINTR_PRACTICE_SEATS`, unlimited on a self-host, none on the hosted offer) until a grant for that practice: `make practice-plan` (also bundled into the image as `worker/practice-plan.mjs`) calls `setPracticePlan`, audited in the professional's log. A payment provider will be a third `seat_source` whose webhook calls the same function. Lowering seats never ends a link; it only refuses the next acceptance.

65. **Notices carry no words.** `notifications` holds a kind and ids; the sentence is written when it is shown, with the names the reader may see at that moment. The person learns in the app when a practice accepted their invite or ended a link; the professional learns of new links and new reports. A small dot beside Sharing or Practice says there is something new, cleared once the notices were on screen. The professional may opt in to an email per new report (`practices.notify_email`, to a confirmed address): the worker sends a link and a count, never a name or a word, and claims each report before sending so it is told at most once.

66. **The dashboard centralises access, not analysis.** It counts active patients and seats, lists pending invites, patients and received reports by recency, and opens a report in place beside the list (`/practice?report=`), set with the same paper as the person's own page. Report links are never prefetched, because opening one is a recorded reading. There is nothing computed across patients.

67. **A neutral label, and the name on the report.** A person who chooses no name for the link is "Patient N" in the practice's list, N being the practice's own count, assigned with the practice row locked. The report itself is the approved one: if the person put a name on their reports in Therapy ("Your name, as the report shows it"), it is printed on every report, the shared copy and its PDF included, as on an emailed one. So the screen does not promise more than the list: it says "In their list they see you as Patient 3" and, when there is one, "Your reports show the name you set in Therapy, ...", on the link and before accepting.

68. **The crisis lines stay with the person.** Every page of the person's side and the invite page keep CVV 188 and SAMU 192 in the footer. The practice pages replace them with a note for the professional: reports arrive when a person approves them, never in real time, and sintr is not a monitoring tool or a crisis channel.

## F5 the house model and the plan

69. **The house assistant comes from the environment, all or nothing.** `SINTR_HOUSE_PROVIDER`, `SINTR_HOUSE_BASE_URL`, `SINTR_HOUSE_MODEL`, `SINTR_HOUSE_KEY` and `SINTR_HOUSE_NAME` configure one provider, one model and one key for the installation; a missing piece stops the start with the variable's name, never its value. The key lives in the process environment and in memory only: never in the database, never in a page, never in a log (tests check the pages, the logs and the person's stored settings). Its address is the operator's, so it may point at a gateway on a private network even on the hosted offer, where a person's own address may not (decision 20). Keys are still always passed explicitly (decision 19). `SINTR_HOUSE_NAME` is what people are told receives their words ("Anthropic"); by default it is the provider's name, or the host of an OpenAI-compatible gateway. On the hosted offer a gateway must have a key and a name: a gateway that answers without a key could be used by anyone as their "own" provider, uncounted, and its host name says nothing about who receives the words.

70. **The person's own key comes first, and never falls back.** `resolveAssistant` answers with the person's own key whenever they saved one, the house assistant otherwise, and nothing when there is neither (the app then points to the door for a key). A key of theirs that is broken is reported as it was before; it is never replaced by the house's, because that would send their words to a provider they did not choose. A person's own provider can never be the house's own address (that would be the house, uncounted), and on the hosted offer a single host name without a dot is refused like a private address. Going back to the included assistant removes their provider settings and key, audited as `agent_key.removed`.

71. **Bring your own key is a small door.** With a house assistant, Settings says the assistant is included, who receives what is written and the plan's count, and the key form waits behind a closed disclosure, "Use your own key instead". On the person's own key, one line says what changed (their provider, not counted toward any plan) with a button back. Without a house assistant (a typical self-host) the same form is the way in, and the door stands open. The behaviour of a saved key is unchanged from F1 (decision 18).

72. **Plans and their numbers.** Free: 100 messages with the assistant, 4 reports written by it and 15 audio minutes a month. Personal: 600, 12 and 120. Unlimited exists for installations that want no limit (`SINTR_PERSON_PLAN=unlimited`, or a grant). Audio is a placeholder: the number is set and shown nowhere, and nothing counts it until audio arrives. Why these: an honest week is two to five difficult moments told in four to eight messages each, plus a few check-ins told in Talk, so 20 to 50 messages; a heavy month is about 190. Personal is three heavy months in one, so an honest week never meets it, and anything near 600 is not a diary. Free covers a light month whole and a heavy one for about two weeks, enough to feel what the assistant does before deciding. Reports follow sessions: four or five a month for weekly sessions, so Free covers a month of them and Personal leaves room for twice-weekly sessions and preparing again. The cost side: the capture instructions are about 1,100 tokens and the tools about as many, so a reply with a draft is two calls of 3,000 to 4,000 tokens; on a small current model (in the order of 1 USD per million tokens in and 5 out) that is about one cent a message, so a fully used Personal month costs the house in the order of 6 USD and a fully used Free month about 1 USD, with reports adding cents. The price of Personal has to sit above the first with a margin; the cost of an abandoned Free account is bounded by the second, and sign-up is limited to 10 every 10 minutes per address (PRIVACY, Authentication). The numbers live in code (`PERSON_PLANS`); changing them is a decision recorded here.

73. **"Pro" became Personal.** PRODUCT named the tiers Free and Pro. "Pro" reads as "for professionals", which is the practice's side. A person is on Free or Personal; a practice is on its Free seat or the Practice plan.

74. **The meter is a month of the person's own calendar, keyed by the month.** Counts are kept per calendar month in the person's time zone, under the month's first day (`usage_counters.period`), so changing time zone can only move which month a unit lands in, never open a month twice. It is not the billing period: subscribing mid-month adds the rest of Personal at once, and the count always "starts again on 1 November", which needs no explanation. The billing period is shown separately, as the date the subscription renews.

75. **Take before the call, refuse in the same statement, give back after a failure.** One unit is taken right before the house model runs, by an insert that adds one only while the count is under the plan's limit, so two tabs cannot both take the last unit; a test runs twenty in parallel against a limit of four, and fails with the condition removed. A reply or a report that fails gives its unit back to the month it was taken from. Unlimited plans are counted too, so whoever runs the installation can see the use.

76. **What counts, and what never does.** One unit per message the house assistant answered (a reply with its tool steps is one) and one per report it wrote and sintr stored (preparing again counts again, and so does the scheduler bringing an early draft up to the session). Never counted: a message the crisis screen stops (no model runs), a "salva" at the limit, anything on the person's own key, a reply that failed or a turn that broke before it, a report that was not stored (another preparation of the same period got there first, or the person left). Over the month's reports, the scheduler leaves a draft the assistant wrote as it is rather than replace it with a thinner one. A paused conversation's model replies count, so a paused conversation is no way around the plan; at the limit it still gets the fixed message with CVV 188 and SAMU 192, without a model.

77. **At the limit, the words are kept.** The model does not run; the person's message is stored as always and offered back as a draft entry, their words verbatim as what happened, timed now, to confirm, change or discard like any draft. A "salva" still saves. sintr's reply is a data part written by the app, not text in the assistant's mouth, so the model never reads later a reply it did not write. Before the person types, Talk says so above the composer: what happened, what still works (writing here, check-ins, the report), when the assistant answers again, and two ways on (the plan, their own key). A report over the month's allowance is prepared by sintr alone (decision 42) and says why. A plan never hides, locks or deletes anything the person wrote; capture comes first (PRODUCT, invariant 2). One thing the limit does take away: the assistant's own recognition of risk (`signal_crisis`, decision 23) needs the model, so at the limit only the fixed screen runs, exactly as on an installation without a provider. The help lines stay under the composer on every page, and a message the screen catches still stops the diary. An uncounted model call at the limit, only to look for risk, was considered and left out: anyone could then spend the house's key without limit by writing at the limit.

78. **A quiet word before, and nothing else.** Under the composer, one caption: "The assistant is included in your plan." In the last tenth of the month's messages (or the last five), it says how many are left and the date they start again. No banner, no modal, no email, no colour; the plan screen's meters are graphite on a hairline, and the words carry the state.

79. **The practice plan: seats, and the assistant for the professional's own diary.** A practice with a plan of its own (granted, or paid) includes Personal for the professional's own account. It does not cover its patients: sharing with a therapist must never change what a person has, or stopping would cost them something, and a consent that costs something to withdraw is not freely given (LGPD art. 8). The practice sees seats, never anyone's use of the assistant. A hosted practice without a plan of its own gets one free seat, so a therapist can try sintr with one patient before paying (F4 gave none). A self-host keeps unlimited seats.

80. **Subscriptions, modelled once for both sides.** `subscriptions` holds one row per account and kind (`person`, `practice`): the plan, the status, the source (`grant` or `stripe`), the seats, the period, whether it ends at the period's end, and the provider's customer and subscription ids. Active, trialing and past due keep the plan (past due while Stripe retries the payment); anything else does not. `make person-plan EMAIL=... PLAN=personal|unlimited|default` is the person's admin path, next to `make practice-plan`; it refuses to overwrite a plan the person pays for, and a paid subscription replaces a grant (one that was never paid, incomplete or cancelled, does not). A practice's seats still change through one function (`writePracticePlan`), now with a third seat source, `subscription`; lowering seats never ends a link (decision 64), and `make practice-plan` refuses a practice whose seats are paid.

81. **Stripe, over HTTP, behind configuration.** Off unless `SINTR_STRIPE_SECRET_KEY`, `SINTR_STRIPE_WEBHOOK_SECRET` and a price are set. Stripe because it works in Brazil (reais, cards, and Pix through Checkout), hosts the payment page and the billing page (no card data ever reaches sintr), and signs its webhooks. No SDK: four calls with `fetch` (a Checkout session, a billing page session, a price, a subscription). The webhook checks the signature over the raw body (five minutes of tolerance, compared in constant time), ignores every event that is not about a subscription, then reads the subscription back from Stripe and applies its current state, holding a lock on that subscription from the read to the write: events that arrive late, twice, out of order or at the same moment cannot move a plan backwards, and when Stripe cannot be read the answer is 503, so Stripe delivers again. A subscription sintr already follows keeps being followed after its price stops being sold (a raised price must not leave old subscribers' cancellations unapplied); the price is checked only for one it does not follow yet. The content security policy lets a form go to Stripe's two pages, so subscribing also works before the page's script has loaded. A subscription carries the account's id and kind in its metadata; one for an unknown account, a price this installation does not sell, or a second active subscription of the same kind is not applied, and is logged as a code. What Stripe receives from sintr: the account's id and email, the plan and the seats.

82. **No phone-home.** Plans need no network: entitlements are read from the database. The price on the plan screen is read from Stripe only when payments are configured, cached for an hour, and left out if it takes more than a moment. A self-host without `SINTR_HOUSE_*` and `SINTR_STRIPE_*` works as before, offline, on the person's own key or a model on the same machine.

83. **The end-to-end suite runs the same build twice.** One server is the self-host without a house assistant (the earlier suites, unchanged); the other runs as the hosted app would, with a house assistant and payments against a fake Stripe on the same machine (`e2e/fake-stripe.ts`). Both use the rehearsal model (decision 28) in place of whichever model would answer. The worker's integration test goes one step further down: the house's real adapter, address and key, against a fake OpenAI-compatible endpoint (`scriptedEndpoint`). No test reaches a real model or Stripe, so how a real model behaves on the house path is not what they show.

## F6 the first five minutes

84. **The welcome, and what it asks.** After signing up the person lands on `/welcome`: a calm first screen, then one question a screen (how they want to be called, the practice invite they arrived with if there is one, their therapist's name, when the sessions are, with the time zone taken from their device), then the home. Each answer is saved as they go on, and each can wait. Nothing in it asks for a provider, a key or a card, or for anything the product can do without. The steps live in the address (`?step=`), so a phone's back gesture goes back a question. It is not forced afterwards: until it is finished or set aside (`profiles.onboarded_at`) the home offers one line to pick it up, and nothing else. Everyone who had a diary before F6 is marked as done by the migration. A professional who signs up to accept a person's invite is taken straight to that invite: there is no diary to set up for them there.

85. **The name a person goes by is not the name on their reports.** `profiles.preferred_name`, sealed, is used to greet them on the home and nowhere else: it is never sent to a model (the assistant does not need it to keep a diary) and never printed on a report. The name on reports stays the explicit choice in Therapy (decision 67): a report goes to a therapist, and a name given for a greeting is not a choice to print it there. The welcome says so under the question. On a practice's invite, "how they will see you" starts from it, and the person sees it before accepting.

86. **Speech is counted to the second.** F5 set 15 and 120 audio minutes and left an `audio_minutes` column for them. Counting whole minutes per recording would let fifteen short recordings use a free month, so `usage_counters.audio_seconds` counts seconds and the plan shows started minutes ("1 of 15"); the F5 column stays, unused, because migrations are additive. A recording is taken whole before the call, by its length as the browser measured it, but never less than its size makes it at 256 kbit/s (the browser records at 64, so an honest recording is always longer than that floor) and exactly its length for WAV, read from its header; one whose floor is already past five minutes is refused before anything is taken or sent. It is refused in the same statement once the month is used; after the call it settles to what the provider counted (OpenRouter's `usage.seconds`), and a call that failed, for any reason, gives it all back. Where the provider says nothing of the length (Groq, OpenAI's newer models, Gemini without WAV), the browser's measure stands, held up by that floor. A recording that starts with time left is never cut, so words already spoken are never thrown away; the browser stops recording when the month's time runs out, so a month is passed by one recording at most. Only the house is counted.

87. **Who writes down what is said: the provider that already answers.** On the house: its own provider and key (OpenRouter's `/audio/transcriptions` with `openai/whisper-large-v3-turbo`, the endpoint and model the owner's own assistant uses), or a transcription endpoint of its own for a house whose provider takes no audio (`SINTR_HOUSE_STT_BASE_URL` and `SINTR_HOUSE_STT_KEY`, for an Anthropic house), or nobody (`SINTR_HOUSE_STT_MODEL=off`); `SINTR_HOUSE_STT_MODEL` may name another model. On a person's own key, the same provider they chose, by its best path: OpenRouter's Whisper large v3 turbo, OpenAI's `gpt-4o-mini-transcribe`, Groq's `whisper-large-v3-turbo`, and for Google, Gemini itself listening, with the recording sent as WAV (Gemini reads neither WebM nor MP4 audio) and an instruction to write it down word for word and nothing else. Anthropic takes no audio, and an OpenAI-compatible endpoint sintr does not know (Ollama, LiteLLM) is not guessed at: in both cases the home shows the box and one line that says so and names the providers that can listen, never a button that does nothing. Never the house for someone on their own key: their words would go somewhere they did not choose (decision 70). Requests are multipart, as the OpenAI SDK sends them; keys are passed explicitly and a person's address is held to the hosted offer's rules, redirects refused (decisions 19 and 20). The privacy settings of the account at OpenRouter (zero data retention, no training) apply to transcription as they do to the conversation; sintr adds no routing of its own.

88. **The audio is used, then dropped.** The recording goes from the browser to sintr's server in one request, is held in memory for the one call to the transcriber, and is dropped: never written to disk, to the database or to a log (the log has a code and the seconds). Nothing is kept on the device either. Keeping it was considered and left out: a voice would be the most identifying thing sintr holds, for nothing the diary needs. The words are what the person keeps, and they read them first.

89. **The transcript waits for the person.** What comes back lands in the box with "Here is what I heard. Change anything, then send it.", and is nothing until they send it: speaking creates no conversation, no message and no draft. Once sent it is a message like a typed one: the crisis screen runs on it before any model, drafts are checked against it, and nothing becomes an entry without Confirm or "salva" (decisions 21 to 23). The screen also runs on the transcript the moment it comes back, and if it matches, the help lines open above the box before anything is sent. The transcription itself is a model call that no text screen can come before, since it is what makes the text; the help lines are on the screen beside the Speak button before the first word.

90. **The language hint comes from the person's own writing.** Whisper writes down better with the language it is told, and worse with a wrong one. The hint is, in order: the language of the person's own messages in this conversation (or their latest one), when enough telling words make it clear (Portuguese, Spanish or English); the report language they chose in Therapy, unless it is the default, English; `SINTR_HOUSE_STT_LANGUAGE`; and otherwise none, and the provider tells from the audio.

91. **The home is the input.** `/home` replaces Entries as where the diary opens (after signing in, from the wordmark, after the consent): a greeting for the hour, one question, the pool of light, the box, and Speak where the thumb rests while the box is empty. `/talk` redirects to it, and a conversation keeps `/talk/<id>`. Everything else is a sentence away under the question (a check-in, the report, what you kept) and in the navigation. On a phone the nine tabs became one Menu sheet that says what each section is for; from 900px the side list stays as it was.

92. **The light follows the person's hour, and moves as the site moves it.** The window light's colours are registered properties that cross-fade over 2.8s, and its place changes with the scene over 3.4s (each step of the welcome, the home, a conversation, speaking), with only transform and opacity moving so nothing is repainted. Its palette is the person's own time of day: their time zone on the server, their device's in the welcome. On a phone it is one oversized pane that stays put and only changes strength, and its leaves do not sway: their blurred shadow is painted again on every frame, and that was the whole cost measured on a phone (40 frames a second with it, 60 without, with the CPU four times slower; the pool and the drifting light cost nothing measurable). On a wide screen with a mouse they sway as on the site; there, in headless Chromium without a GPU, the home ran at 17 frames a second where the live site runs at 9 under the same conditions, so it is lighter than the site it follows; real graphics hardware composites these layers, and was not measured here. The light sits under the words, as on the pages before, so no text loses contrast; reading pages keep it in the header. Reduced motion keeps every state and drops every movement (no animation runs at all).

93. **A pool of light, not a pastel blob.** DESIGN rejects the wellness-app blob. The home's presence is a small pool of the same window light: the light's colours at that hour, a little deeper so it reads on white, blurred once and then only turned and scaled (no shape morphing, which would repaint every frame), multiplied onto the paper; no face, no gloss, no outline. It rests, listens (its size follows the voice's level, smoothed, written to a CSS variable without re-rendering), gathers while what was said is written down, pulses while the assistant answers, warms while a draft waits, and goes still and grey when the diary is paused. What it is doing is said in words for screen readers and, in a conversation, in a short caption beside it. Its states come from one function, tested on its own.

94. **Strings live in a catalog.** `apps/web/messages/en/<feature>.ts`, one file per screen or feature, typed, with a function for each sentence that carries a value; components read `t.<feature>`. Every string written or rewritten in F6 is there; strings of F1 to F5 that F6 did not touch move when their screen is next rewritten. The languages milestone adds catalogs beside `en`.

95. **The microphone, for sintr's own pages only.** `Permissions-Policy` now says `microphone=(self)` (it said `()`), so the home can ask; nothing a page embeds can, and the camera and the rest stay off.

96. **Less form, where a form was too much.** The check-in is a few taps, one question a screen, a tap on a number moving on and any question skipped; it is still one form underneath, so without JavaScript every question shows at once and it saves. Therapy opens on three sentences (the sessions, the therapist, the report), each opening its own part to change, and a part with a problem opens by itself. An entry's form keeps what happened, the thoughts and the feelings in front and the rest behind "More about it". Settings and Connect speak of your assistant, your other assistants and your therapist.

97. **The tests' microphone and transcriber.** Chromium's fake device plays a tone, which the browser really records; `SINTR_FAKE_AGENT` also replaces the call to the transcriber with the rehearsal transcriber, which checks that a recording arrived and answers one sentence, whoever's route it stands for. The route is still decided as in production, so which provider would hear the person, the meter and the refusals are what the end-to-end tests show; the agent's tests check the request each provider would get on the wire, against a fetch that never leaves the process. No test reaches a real transcriber, so how a real one hears a real voice is not what they show.

## F7 the same app in your language

98. **Who decides the language, and where it is kept.** For every request, in order: the person's own choice; the installation's language (`SINTR_LANGUAGE`); the first of the browser's `Accept-Language` languages that sintr has a catalog for, by weight (a variant answers with the language sintr has: `pt-PT` reads Brazilian Portuguese); English. It replaces decision 17. The page's language is decided once on the server (`currentLanguage`), so `<html lang>`, server components, actions, API routes and the client components (through a provider) all read the same one; nothing in the browser decides it. The choice lives on the profile (`profiles.locale`, null until chosen), so it follows the person to every device; made before signing in, it lives in an HTTP-only cookie that holds only the tag, and signing up with it keeps it as their choice. It is changed in Settings, said as a sentence with who decided it ("as your browser asks", "as you chose"), or with a quiet line at the foot of the page that offers each other language in its own words ("Ler o sintr em português"); "Let sintr choose" gives the choice back. Both are a plain form post to `/api/language`, which works without JavaScript: the page sends no referrer (`Referrer-Policy: no-referrer`), under which a browser posts a form with `Origin: null`, so the route checks `Sec-Fetch-Site: same-origin`, which no page can set, and the origin only for a browser that sends no such header (a server action would refuse that post). What sintr writes while the person is away (a scheduled report, a "report ready" email, a practice's notice) cannot read a request, so the language a page was last shown in is kept too (`profiles.seen_locale`, written when it changes, and at sign-up from the sign-up page); those use the person's choice, else that, else the installation's. The browser's other languages are never stored.

99. **Languages are data, like the site's.** Every word of the app is now in the catalog: F7 moved the strings of F1 to F5 that decision 94 left in their screens. A language is a folder, `apps/web/messages/<code>/`, with one file per screen or feature in the shape of English's, and one line in `apps/web/messages/languages.json` (its code, its own name, how it writes dates, the browser languages it answers), as the site's `i18n/locales.json` lists its pages. The bundler has to see the folders as imports, so `scripts/languages.mjs` writes the one module that imports each listed catalog (`languages.generated.ts`); the web app's dev and build scripts run it, so the image a self-hoster builds always has every listed language, and `make lint` and the parity test fail when the committed module is out of date. A discovery by the bundler alone (`require.context`) was considered: it works in webpack but not in the tests or the type checker, and an unlisted half-translated folder would be served. Catalogs stay TypeScript, typed by English's shape with every sentence widened to a string, so a sentence with a value is a function and each language writes its own grammar; JSON with placeholders would have needed plural and gender rules of its own. A language may leave out a whole screen, which is then read in English whole; a key cannot be missing inside a screen (the types refuse it), so nothing renders half in one language or as a key. The parity test fails for any listed language that misses a screen, a key or a list item, has a key English does not, leaves empty a sentence English says, or re-exports English; it also runs the copy rules over every sentence of every language, functions written out. Every listed language travels to the browser in one chunk, so a client component reads any of them synchronously and hydrates with the page's own: with English and Portuguese that chunk is 164 KB, 49 KB compressed, on every page. That is the cost of a handful of languages; past that, each language should become its own chunk, loaded for the page's language only.

100. **The report's language follows the person's unless they chose one.** Until now `profiles.language` was the report's language, English unless changed in Therapy, so a person reading sintr in Portuguese got English reports by default. It now lives in `profiles.report_language`, null meaning "the language you read sintr in", which is Therapy's first choice and names that language; English, Portuguese and Spanish stay as explicit choices for a therapist who reads another language. The migration copies the old value where it was not English, the only case known to be a choice; `profiles.language` stays, unread, because migrations are additive. The report keeps its own words in its own three languages (decision 41): a stored report carries the language it was written in, so changing language later changes the app around it, never a report already prepared.

101. **What sintr writes without a page speaks the person's language too.** The emails about an account (a report is ready, a new password, the address confirmation, a report shared with a practice) are written in English and Portuguese in core, beside the report's own words, and any other language gets English; the report to a therapist already follows the report's language. The password and confirmation emails are written as the request that caused them is read: Better Auth hands the request to its callbacks, and the web resolves it exactly as it resolves a page. Finding the language reads the profile, so it happens after the answer like the send itself: neither the time it takes nor its failure tells the browser whether an address has an account (decision 39). The worker passes the installation's language for people who never opened sintr since F7.

102. **The assistant and the voice follow the person, the instructions stay.** The model-facing instructions are unchanged; the line that tells the model the person's app language now carries the language resolved for the request rather than the report's, and the model still answers in the language the person writes in. The fixed message that stops the diary is chosen, as before, by the language the screen recognised in the person's words, and otherwise by the language they read sintr in. The transcription hint is, in order, the language of the person's own writing (decision 90), the language they read sintr in when something set it (their choice, the installation, their browser; not English only because nothing else did), then `SINTR_HOUSE_STT_LANGUAGE`.

103. **The help lines in every language.** Every page keeps Brazil's lines (CVV 188, SAMU 192) and findahelpline.com for anywhere else, worded in the page's language and rendered on the server with the page, so they are there without JavaScript. Lines for other countries are a decision of their own, not a translation. The screen for risk runs before any model in every language, as before: its patterns read Portuguese, English and Spanish whatever the page's language, because a person may write in a language other than the one they read sintr in.

104. **The consent is the same in every language.** The words a person agrees to (sign-up, a practice's link, a send, a share) are translated with the same meaning, nothing softened or added, and keep their version: the version names the meaning, and what was recorded is that the person agreed to it. A change of meaning in any language is a new version for every language at once.

105. **Spanish is ready, not shipped.** The report, the therapist's email, the crisis message and the screen's patterns already speak Spanish, and the voice reads Spanish writing. What a Spanish sintr still needs is its app catalog (a folder, and a line in `languages.json`), and its account emails, which fall back to English until core has them; no Spanish strings were added in F7, as the brief asked. A language beyond those three also needs the report's printed words and the crisis screen's patterns, which are code and are reviewed as code: a screen for risk is not a translation. `docs/LANGUAGES.md` says this to a self-hoster in that order.

## F8 the assistant everywhere

106. **The assistant lives in the shell, so it is one conversation everywhere.** The conversation, the words in the box, the voice, the drafts' decisions and the month's meter used to belong to the home's page; they now belong to the diary's shell (`AssistantProvider`), which stays mounted while the person moves between pages, and the home and the corner are two views of it. Started beside Entries, a conversation is the one the home shows; words heard or typed and not yet sent go with the person to the next page; a page that opens a conversation (`/talk/<id>`) hands it to the shell. It is the same assistant and the same conversation on every page, and it knows nothing of the page it is on, as the brief asks. The shell reads, with the frame, only what the screens already showed (who answers, the meter, how the person can speak, never a key); a change of assistant in Settings refreshes the frame. The server is still the record (decision 24): a new conversation lets the current one go to the list, a page loaded again starts from the server, and deleting a conversation forgets it in the shell too. Only the home gives a conversation its own address; beside another page the page keeps its own.

107. **The home is the assistant's room, and every other page of the person's diary carries it in a corner.** On the home the pool rests in the middle, large (232px on a desk, 168px on a phone), with the greeting, the question and the box under it (at the bottom of a phone, where the thumb rests) and the doors to everything else under the box; earlier conversations stay below the fold. Everywhere else in the person's diary (entries, check-ins, Therapy, reports, Sharing, other assistants, Settings, the plan) a small round window of paper holds the same light and opens the conversation beside the page: at the foot of the side list on a wide screen ("into a sidebar", in the owner's words), beside the Menu in the header of a phone, where the header now stays at the top (clear over the light at first, paper with a hairline once the page scrolls under it). A window floating in the bottom right corner was built first and walked: at rest on a phone it sat on the help line's call button, and on a narrower desk over the end of the text, so it moved to places that cover nothing. The window stays while the conversation is open, empty, and closes it again. The practice's pages carry neither the assistant nor the help lines (decision 68): they are the professional's desk, and the help lines go with the assistant. Without any assistant (a self-host before a key) there is no corner, rather than a button that leads to a setup notice.

108. **One pool travels, as a shared element, not a view transition.** The pool rests in one place at a time (the middle of the home, beside the box once a conversation begins, the corner, the conversation beside a page). When one place goes and another comes, the shell measures where the pool was just before the change (React's snapshot before an update, so the page has not moved under it yet) and carries one square across the screen to the new place, moved and scaled about its centre with the Web Animations API: transform only, on the compositor, so a busy page does not stall it. The way across eases on the light's slow in-out and the way down a little later, so the path bows gently; it takes 0.9 to 1.5 seconds by distance. The pool's own movements (its breath, its layers turning) are handed over by their clocks, so the pool that lands is the pool that left. It takes no pointer, so it never stands between the person and a button, and it never flies to or from a place out of sight. With reduced motion it is simply in each place. A view transition (React's `<ViewTransition>`, or the browser's own) was considered: it freezes the page into snapshots and holds the page's input while it plays, which is a second here, and the Next.js in use would need React's experimental build for it.

109. **Beside the page, never over it.** The conversation opens as a panel on the right of a wide screen and as a sheet from the bottom of a phone (under 720px), which sits on the keyboard rather than under it (from the visual viewport). It is a dialog that is not modal: the page stays where it was, readable and usable beside it, focus can leave it, and closing it (Close, Escape, the corner's window again, a tap on the page beside a phone's sheet) returns focus to the corner and the person to the same place on the page. Opening it moves focus to the box on a desk and to the panel on a phone, so no keyboard jumps up. Escape while the microphone listens stops listening first. The microphone is open only while a conversation is in view: closing the panel or leaving a page keeps nothing heard (decision 88), and words already being written down still arrive in the box. A draft confirmed beside a page is written and the page under it is read again (`router.refresh`), so Entries shows the new entry at once. What the assistant is doing is said once for the whole diary to screen readers, and in the corner's name ("Talk to sintr. A draft is waiting for you").

110. **Still when nobody is there.** The pool and the window light used to move for as long as a page was open. After twenty seconds without a touch, a key or a scroll, the app marks the page idle and every animation of the light pauses where it is, so no frame is drawn for it; the next touch carries it on from the same place. It never pauses while the assistant listens, writes down or thinks.

111. **A session that moved is not a setting any more.** Therapy asked "Has a session moved?" for a one-off date that took the place of the weekly session nearest to it (decision 34). The owner asked for it to go: it read badly, it was poor to use, and it did not make sense, because when a session moves the person can prepare that week's report on the day, from Reports ("Prepare it now", decision 36), and it covers the days since the last report up to that moment. The field, its check box and its sentences are gone, and so are the planner's one-off rule and the worker's reading of the date; this replaces that part of decision 34. The weekly schedule stays, and so does a draft following a changed weekly day (decision 35). `therapy_settings.next_session_at` stays as a column, because migrations are additive, and migration 0008 empties it, so no date set before can go on moving a report that nobody can see or change any more.

112. **The welcome, again, with nothing erased.** One line under the Settings heading offers the welcome again and says what it does not do: "nothing you have written is erased". Run again (`/welcome?again=1`), it opens on a sentence that says so, every answer already given is in its field, and every question has a Skip that keeps the stored answer (and puts back anything changed in the field), so the summary at the end says what is stored. A first welcome's "I do not have one right now" is a skip that empties the field; run again, Skip keeps the therapist. Nothing in it can touch the diary, and "Not now" goes back to Settings. A confirmation before starting was considered and left out: nothing is lost by walking through it.



## F9 nothing leaves the page unsaved

113. **A guard that knows what is unsaved, and asks only then.** Settings has several forms, each with its own Save, and moving to another page used to throw a change away without a word. Each form now tells the guard what its fields are called (`useUnsaved`, `components/unsaved.tsx`): the time zone, how long to keep conversations, the assistant (provider, address, model, key and the box that removes it), the language. A form is unsaved when its fields differ from what stands saved: what the page brought, then what each successful save sent. What the page brought is read from the form's own defaults, so a box ticked on a slow phone before the page came alive still counts. Touching a field is not a change, and a change undone by hand is no change. The key and the box that removes it are emptied by the form once saved, so they count only while they hold something. The guard lives in the diary's shell, so it hears the navigation's links as well as the page's, and it is inert until a form joins it: today only Settings' forms do, and any other form can join with the same hook. It listens for a way out only while something is unsaved, and a save that went through makes it forget at once, so nothing stale is left behind. What a form saves, how and where is unchanged.

114. **Every way out asks, as far as a page can ask.** A link anywhere on the page (the page's own, the navigation, the menu on a phone, the assistant's panel) is caught before Next's router sees the click, and played again if the person chooses to leave, so the link does exactly what it would have done. A link that opens elsewhere (another tab, a download, a call) or stays on the page is let through. A plain form the browser sends itself loads another page: the language form's own change goes with it, so it is asked about only when something else on the page would be lost, and the language links at the foot of the page likewise. "Go back to the included assistant" opens Settings again at another address, which starts the page over, so it says so (`data-leaves`) and is asked about too; signing out asks before it signs out. The browser's back and forward within the app are asked about through the Navigation API, which lets a page cancel a step inside its own document after the person has used it (Chrome and Edge, Firefox from 147, Safari from 26.2); in a browser without it, a step back inside the app is not asked about. Reloading or closing the tab, and a step back to another site, can only get the browser's own question, which says nothing of what would be lost; that is the browser's rule, and it is what the brief accepts. Pushing a copy of the page onto the history, so that Back lands on it first, was considered and left out: it leaves an extra step behind after every save and every knowing exit, and fights the router for the history. Without JavaScript the forms post as before, nothing asks, and nothing is lost that the page would not have lost anyway.

115. **The question is one sentence, and staying is the default.** A native modal `<dialog>` in the page's language says what would be lost, in the page's order ("Your changes to the time zone and the assistant are not saved yet, and leaving now would lose them."), joined as the language joins a list, and offers two pills: Stay on this page, filled in ink and focused, then Leave without saving. Escape and a tap beside it stay, and focus goes back to where it was. No alarm and no guilt: no red, no icon, no "Are you sure?". It is a card in the middle of a wide screen and a sheet from the bottom of a phone, and with reduced motion it is simply there. A mark on the page while a change waits ("not saved") was considered and left out: this milestone is the moment of leaving, and a mark is one more thing to clear after a save.

## F10 a memory that knows the person

116. **The memory is the person's own diary, kept short, for their own assistant.** The assistant in the shell knew the conversation in front of it and, when it asked, the last seven days (decision 25); the owner asked for it to know who the person is, what has been going on and what happened before. Three kinds of memory: how they want to be called (`name`, from the welcome), who they are (`about`: the people in their life by the names they use, their work, where they live, what matters to them) and what happened (`moment`, dated by its page). Every one comes from one entry or one check-in note, and carries the person's own words it rests on: the model that answers the person reads a few pages at a time and proposes memories through one tool, and sintr keeps only those whose quote is found in their page word for word (the finder of decision 22, so what is stored is the person's span, not the model's copy), whose sentence states no cause and uses no clinical label (the patterns of decision 33), and in which the crisis screen finds nothing; at most four from a page; a refused one goes back to the model with the reason, twice at most, and the quote decides the page (a memory the model labelled with the wrong page is kept with the one page its words are on). The sentence is a condensation, as a report's prose is (decision 32); a thought is never paraphrased into it, the quote carries it, and the instructions forbid assuming a gender or turning one event into a trait. Conversations are not a source: what matters in one becomes an entry when the person confirms it, and conversations expire (decision 27). Therapy notes and reports are not either. Nothing of the memory reaches MCP, a report or a practice (decisions 50 and 60 are unchanged): it exists for the person's assistant in sintr. Memory, a section of the person's diary, shows every memory with the page it came from and the words under the highlighter (they are a quotation of the person), and lets them correct one, forget one, forget everything, or download it.

117. **What a dump of the memory reveals, and what it does not.** A memory's sentence and quote are sealed like the diary, with the person's key and `memories.text` and `memories.quote` as associated data. Its vector cannot be: pgvector compares vectors in the database, and a sealed one cannot be compared. A provider's vector stored as it came would not be plaintext, but it is close to it: inversion models trained on a provider's embeddings recover much of a short text from its vector. So each vector is stored turned by a rotation that only the person's key describes: a random orthogonal matrix in Stewart's construction (a product of Householder reflections with Gaussian directions, after random signs), drawn from AES-CTR keyed by HKDF of the person's data key, never stored, drawn again when needed (about 50 ms for 1536 numbers) and gone with the data key. A rotation keeps every angle between one person's vectors, so pgvector's cosine distance finds the same neighbours; the question is turned the same way before it is compared, so neither the provider's vector of a memory nor of what the person said ever reaches the database. A dump of `memories` was made on this branch from real embeddings (OpenRouter, `openai/text-embedding-3-small`) and read. It shows, per person: how many memories, their kind, which entry or check-in each came from, the date of that page, when each was kept or corrected, the model's name and length (`openai/text-embedding-3-small@1536`), the sealed envelopes, and 1536 numbers per memory; `memory_reads` shows which page was read and when. None of the words appears in it, in clear or as hex (the at-rest test scans for them), and the stored vector of a sentence has a cosine of -0.03 with the provider's own vector of the same sentence: it is not in the provider's space, so a model trained to invert that space has nothing to work on. What it does reveal, on purpose: how alike any two of one person's memories are (their angle is the provider's). The limits, said plainly: this is not encryption. Solving for the rotation takes the words and vectors of about as many of that person's memories as the vector has numbers; lining a person's few hundred vectors up with a corpus of the provider's could at best recover general directions, and has not been shown for so few, nor is it ruled out. Two people's vectors are in different rotations, so comparing them means nothing. Anyone holding the master key holds everything, as for the rest of the diary.

118. **The providers that place memories by meaning, and the consent that names them.** The memory follows who answers (decision 70): the person's own key first, the house otherwise, never the house for someone on their own key. The model that reads the diary is the one that answers them; the vectors come from the same provider by its known path: on the house, its own provider and key (OpenRouter's `openai/text-embedding-3-small`, checked against the real API on 2026-10-19), or an endpoint of its own (`SINTR_HOUSE_EMBED_*`, for an Anthropic house), or none (`SINTR_HOUSE_EMBED_MODEL=off`); on a person's own key, OpenRouter, OpenAI (`text-embedding-3-small`) or Google (`gemini-embedding-001` at 1536, not checked against the real API here). Anthropic has no embeddings and an endpoint sintr does not know is not guessed at: Memory then says it is not available and names who can. The call is plain HTTP like transcription, the key always explicit and a person's address held to the hosted offer's rules (decisions 19, 20 and 87). The memory needs its own yes, though the conversation already reaches these providers: an entry written by hand went to a model only when a report was prepared or the assistant asked for the week, and the memory sends every page. The yes is a consent of its own (`memory`, versioned, in the append-only log) whose recipient is the list of providers the page named; the page sends that list back and the server refuses the yes if it changed in between (as decision 56 does for a practice). The consent is for those providers: when they change (a key saved or removed, the house renamed or moved), the memory pauses, nothing is read, nothing is placed and nothing is told to a conversation until the person agrees again for the new ones, and then the old vectors are dropped and every memory is placed again by the new provider. A new wording pauses it the same way. Without the consent there is no memory at all: no row, no reading, the worker never lists the person, the conversation is told the memory is off (so the assistant says so instead of pretending), and Memory, Settings and the welcome say what it would do. Withdrawing it is forgetting everything (decision 120).

119. **The memory in the conversation, after the crisis screen.** The capture instructions do not change; after them comes a section with the name the person goes by, up to eight things about who they are, up to three moments of the last two weeks and up to six found by meaning, each dated and with the person's words, and how to use them: as someone who has been listening for months, never as a diagnosis or a conclusion, never to steer, never as something said today, believing the person when they say one is wrong. Found by meaning is a cosine distance of at most 0.6: measured on Portuguese diary pages with OpenAI's small model, related memories sat at 0.3 to 0.5 and unrelated ones from 0.65 up. The driver asks for it only after the crisis screen has passed and the meter has been taken, never in a paused conversation, and goes on without it after six seconds or on any failure: a memory never delays, softens or replaces the screen, and the reply never depends on it. A page the screen stops is never sent to be read, and no memory whose words the screen stops is kept. The screen reads first-person statements, so a sentence the model writes in the third person about risk is held by the instructions, which forbid keeping anything about wanting to die, suicide, self-harm or harming someone, and not by code: that limit is recorded here. This replaces part of decision 85: the name a person goes by now reaches their assistant, as a memory, while their memory is on, and only then; it is still never printed on a report, and the welcome says so.

120. **Correcting and forgetting, and what outlives what.** A correction is the person's: their sentence replaces the memory's and is placed again by meaning, the words it rested on stay, and a new reading of its page never replaces it. Forgetting one memory deletes its row; the dump after it holds neither its id nor its sealed bytes (the end-to-end suite checks both), and its page stays read (`memory_reads`, ids and times), so it does not come back on its own unless the person changes the page. Forgetting everything records the withdrawal and deletes every memory and every record of a reading; a later yes reads the diary from the start. A memory never outlives its source: composite foreign keys delete it with its entry or check-in, a changed page is read again (what was not corrected is replaced), and deleting the account deletes it all (tested). The brief speaks of export and delete paths that exist; deletion exists in the core (`deleteAccount`, entries and check-ins), but there is no export of the diary in the app yet (PRIVACY says it is still to come). So Memory has its own download, a JSON file of every memory with its words, its source and its dates, and not its vectors, which mean nothing outside sintr; the export of the whole diary, when it comes, includes it. A deleted row's bytes stay in Postgres's files until vacuum reuses the space, sealed and turned, and backups keep what they kept.

121. **Postgres carries pgvector, on the same Alpine image.** The stack pinned `postgres:16-alpine`, which does not ship pgvector, and the pgvector images are Debian. A data volume made by the Alpine image, opened by a Debian one, changes the C library under the database: musl compares text byte by byte and glibc by locale (on this machine, `select 'a' < 'B'` is false on `postgres:16-alpine` and true on `pgvector/pgvector:0.8.1-pg16-bookworm`, both `en_US.utf8`), and under musl the database recorded no collation version, so Postgres would not warn while every text index (emails, session tokens, ids) silently fell out of order. Both were tried on this branch with a volume made by `postgres:16-alpine`, main's migrations and 410 accounts: opened by the new image, `amcheck` found all 70 indexes sound and migration 0009 applied; a copy opened by the Debian image started without a warning, `amcheck` found the email index out of order, and looking up one account by its email through that index found nothing, so that person could no longer sign in. So `docker/postgres.Dockerfile` compiles pgvector 0.8.7, checked against its release commit, onto `postgres:16-alpine`, without `-march=native` (an image built on one machine runs on another) and without JIT bitcode; development, CI and the self-host stack all use it. A self-hoster upgrades with `make selfhost-up`, which builds it (the build fetches pgvector from GitHub) and opens the same volume. Migration 0009 first checks that the extension is available and otherwise stops before changing anything, with a sentence that points to SELFHOST in the database's log and the code `pgvector_missing` in the migrate service's (the logger writes codes, never messages; both were seen on a `postgres:16-alpine` without the extension); then it creates the extension, which needs a role allowed to (the bundled stack's owner is). There is no approximate index: a person's memory is hundreds of rows, compared exactly behind a btree on the person and the model, and one index shared by everyone would mix rotations. Another milestone is open with its own migration; this one is 0009, and renumbering is renaming the file and its journal entry and generating the snapshot again.

122. **The worker reads diaries, within a daily bound on the house.** Every minute, `read-diaries` takes everyone whose memory is on and who has a page not read (or changed since) or a memory not placed, one person's scope at a time, and reads at most eight pages, newest first, in one call, then places what it found in one more. Turning the memory on and Memory's "Read them now" do the same in the request, while the person waits, as "Prepare it now" does for a report (decision 36). On the house, at most 100 pages a person a day are read; the rest waits for the next day, and Memory says so. It is not counted on the plan: it is not a message the person asked for, and a person must not pay in messages for writing in their own diary. The bound is what keeps it from being an uncounted way to spend the house's key (the worry of decision 77): measured, three pages were read in about three seconds, so a full day of 100 is in the order of a cent or two on a small model.

123. **The tests' memory, and the real one.** With `SINTR_FAKE_AGENT` the rehearsal model reads the diary too (a moment of each page in the person's words, and their work when a page says it), a rehearsal embedder places words by the words they share, and the rehearsal's reply calls the person by their name and brings up what is related, so the end-to-end suite can see the memory arrive, be found, be corrected and be forgotten. The worker's tests take the house's real adapter to fake endpoints on the same machine, to see what goes on the wire and when nothing does. Neither shows how a real model reads a real diary or uses what it remembers; that was walked on this branch, in a browser, with the house's model and embeddings (OpenRouter): two entries written by talking to the assistant in Portuguese, the memory turned on, then a new conversation. What the model did changed the instructions four times. It assumed a gender and turned one event into a trait (both now forbidden in the reading). It quoted the feelings line, which sintr writes and the check rightly refuses, so a moment was lost on both attempts; it is now asked to quote one line the person wrote, and the refusal says so. In the conversation it called the person by their name unprompted, but answered "afraid of freezing again" by asking them to tell the last time again, with that meeting in front of it; it is now asked to name such a connection briefly, as something the person can correct, and three replays did ("Isso se parece com a reunião de segunda com o Marcos, ou é outra coisa?"). With the memory off it said so, but placed Memory in Settings and the memory in conversations; it is told both now.

## F11 therapy as a calendar

124. **The sessions are a calendar: a series, and the sessions of it that changed.** Therapy held one weekly slot (`therapy_settings.session_day` and `session_time`), and everything after it assumed one session a week. A session is now a row of `therapy_series`, as a calendar's event is: its first day and its time, local to the person, and how it repeats: not at all, every week, every two weeks, every fifteen days (which is not two weeks: it moves through the days of the week), or every week on days the person chooses. Two sessions in a week are two series, or one rhythm on two weekdays. A session of a rhythm is named by its series and its own day in it (`occurs_on`), and a row of `therapy_series_changes` keeps what happened to that one alone: where it moved to, or that it was cancelled. This is iCalendar's model (a rule, the occurrences it gives, an override keyed by the occurrence it replaces), which is also how Google Calendar keeps "this event" apart from the series. Days and times are read in the profile's time zone, as the slot was, so changing zone moves every session with it at the same wall-clock time. Both tables are clear metadata, like the slot the scheduler already read across people: a day, a time, a rhythm and ids, no free text and no column a word could be written into (a test lists their types); the therapist's name and contact stay sealed in `therapy_settings`. A change's series must belong to the same person: the database refuses it otherwise (a composite foreign key, as for shared reports, decision 60).

125. **A session that moved is a session on another day, never a date that guesses (decision 111).** F8 removed "Has a session moved?" because a one-off date took the place of whichever weekly session fell within half a week of it: the person typed a date, sintr guessed which session it meant, and nothing on the screen showed the result. The calendar is the opposite. The person opens the session that moved, on the calendar or in the list, and moves that one; it shows on its new day and nowhere else, says where it was ("Moved from Tuesday 27 October at 18:00"), can be put back, and the report before it is prepared before it. Nothing is inferred from nearness: the planner's half-week rule stays gone, `therapy_settings.next_session_at` stays empty and unread (no code writes it, and 0010 leaves it as 0008 did), and no field anywhere asks for a date apart from a session. What 111 kept stays too: "Prepare it now" in Reports, for anything the calendar does not hold, and an untouched draft following its session when the session moves (decision 35).

126. **Only this one, or this one and the ones after it, said before saving.** Google Calendar asks, after an edit to a repeating event, whether it is for "this event", "this and following events" or "all events". Therapy asks the same thing in the form itself, above the button, so the person sees which sessions they are changing before they change any: "Only this one" (the default) moves that session alone and every other one stays where it is; "This one and the ones after it" starts the new rhythm there, stops the old one where the new one begins (or at that session, if it comes first), and leaves every earlier session as it was, the sessions moved or cancelled from there on taking the new rhythm. "All events" is left out: sessions already held are history, and from the first session "the ones after it" is all of them. A new rhythm cannot be "only this one", so that choice is disabled and says why. Cancelling asks the same: only this one (the rhythm goes on around the gap, which the calendar shows), or this one and every one after it (the rhythm stops there). A session that does not repeat simply moves, or leaves the calendar. A session that has started is read only. Each change is said once kept ("Moved. Only that session changed: the rest of the rhythm is where it was."), so the person knows exactly what moved.

127. **The planner walks the calendar.** `planScheduledReport` now goes through the sessions still to come in order, in the next few weeks (a little over a year for "is there a next one at all"), and each whose preparation time has come gets its report once; two sessions at the same moment are one session for the report. Everything decisions 34 to 36 hold still holds: a report is for a session and prepared `report_lead` before it, it covers the days since the previous report ended, consecutive periods meet exactly, nothing is prepared for a session that already started, and the scheduler is a reconciler that decides from the calendar as it is now. Two cases are new with more than one session a week. When the lead is longer than the days between two sessions, the second report is prepared at its own time and starts where the first ended, rather than waiting for the first session to start. An untouched draft follows its session when that session moved away, was cancelled, or now comes after a session the person added before it; it never jumps to a later session while its own is still to come. An early draft is brought up to its preparation time only while no later report has begun, so no period overlaps another. The worker reads the series and their changes for everyone with a session in their calendar, behind the same consent gate (decision 36): days, times, rhythms, zones and the lead, nothing sealed. Tests run the scheduler every quarter of an hour over eight weeks for a weekly session, a fortnightly one, two sessions in a week, two weekdays with a two-day lead, and a rhythm with one session moved and one cancelled, and check that each session has one report, prepared on time, each period starting where the one before ended; the worker's own tests prepare a fortnightly rhythm, two sessions in a week, and a rhythm with one session moved and one cancelled, against the database.

128. **The weekly slot became a weekly rhythm, in place (migration 0010).** Nobody rebuilds their sessions by hand. The migration turns every slot into a weekly series on the same day and time, starting on the slot's weekday in a week that has already gone by (the earlier of the last change to the settings and a week ago, read in the person's zone), so the next session and the report before it are what they were, and the last week's session is still one the scheduler recognises: a draft prepared for it does not think its session moved. The slot's columns stay, because migrations are additive, and are emptied, so nothing goes on reading a slot the calendar now holds; a test runs the migration on slots set long ago and yesterday, in two zones, and compares the next session with the one the slot gave. The weekly slot stays a valid answer in one move: Add a session suggests every week on the chosen day, and the welcome still asks for one day and one time, which changes the one weekly rhythm going on from its next session (or adds it, next to anything else in the calendar, erasing nothing); "It changes from week to week" leaves the calendar as it is. Over MCP, `therapy_overview` keeps `weekly` ("Tuesday at 18:00", when the calendar holds just that) and adds `rhythms` and the next few sessions, a moved one marked as moved, so an assistant reading the old field still reads it right.

129. **A calendar in sintr's voice, with Google's moves.** From Google Calendar it takes what the owner named: a session added on a date with a repeat that is a choice ("Does not repeat", "Every week on Tuesday", the labels following the chosen day), a series where one session can differ, and a month that is not a spreadsheet. The rest is the house's: hairline rows and no cell borders, today an ink disc, each session a quiet pill with its time (the next one ink, the past ones faint, a cancelled one struck through where it was), the next one also first in a short "Coming up" list with its rhythm or what happened to it under it, and the month's name in the serif. A session opens as a sheet, a panel in the middle of a wide screen and a sheet from the bottom of a phone (a native dialog: focus stays in it, Escape closes it). What the calendar shows lives in the address (`?month=`, `?day=`, `?session=`, `?add=`), so a reload keeps it and a phone's back gesture closes the sheet; with JavaScript the page moves without loading again and the forms call server actions; without it every link works as it is, the sheet sits on the page, and the forms post to a plain route (`/api/therapy/sessions`) that keeps the same things through the same function, because under `Referrer-Policy: no-referrer` a browser posts a form with `Origin: null`, which a server action refuses; the route checks `Sec-Fetch-Site` instead, as `/api/language` does (decision 98). On a phone the day is the target (its sessions are its times), and its panel comes into view under the grid; on a wide screen each session is its own target. The grid is a table the arrow keys move through, a month at a time with Page Up and Down. The week starts where the page's language starts it (Monday for English as sintr writes it, Sunday for Brazilian Portuguese), and month names, weekdays and dates are the page's language in the person's time zone.

## F12 the flow of making a key

130. **The decisions first, the button last.** Vercel's access tokens (a name, a scope, an expiration, then Create), GitHub's fine-grained tokens (a name, an expiration, a description, the owner, the repositories, the permissions, then Generate) and Anthropic's API keys (a name, an expiration, the linked account, a workspace, then create) all ask what a key is for and what it may do before the button that makes it, and show it once afterwards. Connect asked the other way round: one button first, and the name and the access folded under it in "Name it, or choose what it may do", with read and save chosen for whoever did not open the fold. Now the form asks in view and in order, as a person decides: "Which assistant is it for?" (the key's name in the list), "What may it do?" (the three accesses), then Make the key, with the one thing to know before pressing it beside it: "sintr shows the key once, right after you make it." Nothing is folded away. The three steps of how it works come before the form the first time, because they say what is about to happen; a person who already has a key goes straight to the form. This replaces the "one button for a key (name and access optional)" of decision 53.

131. **A name is asked for, as the question a person can answer.** Keys made without a name were numbered ("My assistant 2"), which made a list a person could not tell apart. The name is now required, by the browser and again by the server, and asked as "Which assistant is it for?" ("For example, Claude on my phone"), with its use said under it: its name in the list. When it names one of the assistants on the page, that assistant's steps open first once the key is made (`clientNamed`). Keys made before keep their names; nothing is renamed.

132. **What it may do is chosen on purpose, the least first.** No access is preselected, as GitHub's permissions all start at no access and its form asks for the least that will do: the person picks one of the three. They are offered from the one that reads nothing ("Save only") to the one that also reads ("Read and save") to the one that saves nothing ("Read only"), each as a hairline card with what it does and when to choose it ("Choose it if you only want help writing things down."). The three stay three with their meanings (decision 45); what changed is that none is the default and how plainly each is put. Under them: to change it later, make a new key and switch this one off.

133. **Afterwards, the key says its own limits.** The key shown once now says whom it is for and what it may do, in the words of the form, as GitHub's token page keeps its permissions in view. In the list, the access moved from the small print to a hairline mark beside each key's name, so what each assistant may do can be read down the list. Once the assistant has called, the panel's button reads "Done" instead of "I saved it, hide the key": the key is in the assistant, and nothing is left to keep.

134. **What was taken from the references, and what was left out.** Taken: the order, a name that is asked for, a scope chosen explicitly, the action at the end, the key shown once with a warning before and after, and the key's limits visible afterwards. Left out: expiration. Every reference offers it, because a developer renews a token on a schedule; here an expired key is an assistant that stops keeping the diary on a day nobody remembers, and nothing would tell the person why. In its place, a key whose assistant has not called for over two months (or that was never used in two months since it was made) says so in the list and suggests switching it off (`QUIET_AFTER_DAYS`), which is GitHub's reason for revoking unused tokens, offered rather than done. Also left out: a description (the name does it), a choice of owner, workspace or repositories (one person, one diary), editing a key's access or regenerating it (a key already in an assistant would change under it; a new key and a Disconnect say it plainly, and the list says so), and a question before Disconnect (it is one action, as ending a link is, decision 62, and what was saved stays). `api_tokens.expires_at` stays, honoured as before, and nothing sets it. No migration.

135. **The same flow without JavaScript.** The form posts as a plain form (React's form action for the server action, so the browser sends a POST that Next answers with the key) until the page is alive, then through `submitWith`, so a problem keeps what was typed. Its button no longer waits for the page to be alive: the form posts and holds nothing secret, so the reason of F9's waiting Saves does not apply. That post reached Next with `Origin: null`, which every plain form post carries under `Referrer-Policy: no-referrer`, and Next's server actions throw on an origin they cannot read; decision 98 noted it and gave the language form a route of its own. The middleware now applies decision 98's check before Next does: a post that says `Origin: null` and that the browser marks `Sec-Fetch-Site: same-origin` (a header no page can set) is given this site's origin, the host Next compares it with, and any other post is left as it came. So a server action's form works without JavaScript, the key's and the Disconnect's here, and those of other screens that were already written to post (the check-in's, decision 96). Every assistant's steps are on the page and the checked radio shows one (`.sintr-guides`, with CSS `:has`), so choosing an assistant works without a script, as DESIGN says the segmented control does. "I saved it, hide the key" is a link to the page as it is now, which hides the key the same way. Without a script to look again, the waiting line says to open the page again instead of saying it will change. The copy buttons still need JavaScript; the key and every snippet can be selected by hand.
