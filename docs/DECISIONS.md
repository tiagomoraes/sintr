# Decisions and trade-offs

Short records of choices made while building, with the reason, so they can be revisited deliberately. Newest last.

## F0 foundation

1. **Sensitive columns are declared once.** `SEALED` in `packages/core/src/db/sealed.ts` lists every sealed column. Repositories seal and open through it, the associated data of each value names its `table.column`, and a schema test fails if a `bytea` column is neither sealed content nor key material. One column per field (not one JSON blob per row) keeps partial updates simple and makes the sensitive surface visible in the schema.

2. **Clear metadata, sealed words.** Dates, the 0 to 100 and 0 to 5 scales, sleep hours, kinds and statuses stay in the clear so they can be aggregated without decrypting; every free-text field is sealed (PRODUCT.md, Risks). `entries.peak_intensity` is derived from the sealed emotions and stored clear for the same reason.

3. **Field AAD is column plus owner, not row.** Binding to the row id would need ids generated before INSERT; column plus owner already stops a ciphertext from being moved to another field or another person.

4. **Two exceptions to "every table has `user_id`".** `users` (its id is the scope) and `verification_tokens` (Better Auth creates them before a user exists; they hold no ledger content). The schema test names both.

5. **Subscriptions and usage counters are not in the schema yet.** They belong to billing (F4); migrations are versioned, so adding them then costs nothing now.

6. **Consent at sign-up, enforced on the server.** A Better Auth `before` hook refuses sign-up without the consent flag, and the after-create hook records it. If that record were ever missing, or the wording version changes, the shell sends the person to `/consent` before anything opens.

7. **No email in F0.** Magic link, email verification and password reset need an email transport, which arrives with the report send (F2). Rather than log links (forbidden) or half-enable them, those Better Auth routes are disabled. Consequence: sign-up still reveals that an email is registered, and a forgotten password cannot be reset yet.

8. **"Rotating sessions" means sliding sessions plus a new token per sign-in.** Better Auth 1.7 extends a used session after `updateAge` but does not rotate the token value in place. Cookie caching is off so revocation is immediate.

9. **Middleware sets headers only.** An optimistic redirect in middleware was removed: Next reports the host as `localhost` there, which moved browsers to another origin and failed Better Auth's origin check. Each page checks the session on the server instead; that check is the gate either way, and its redirect is relative.

10. **Every page renders per request.** Required for the nonce-based CSP; the app is almost entirely authenticated pages, so nothing is lost.

11. **The worker has no auth.** The core runtime is split into a base (repositories, maintenance) and the web runtime (base plus Better Auth), so the worker bundle carries neither Better Auth nor the native Argon2 module.

12. **One image for app, worker and migrations.** The Next.js standalone server, plus esbuild bundles of the worker and the migration runner. `SINTR_STANDALONE=1` turns on standalone output only in the Docker build, so local builds use `next start` without warnings.

13. **Dev Postgres on Docker's default bridge.** The dev database does not create a network, so it starts even where a VPN has exhausted Docker's address pools. The self-host stack needs its own network; `SINTR_DOCKER_SUBNET` gives it an explicit subnet on such hosts, through an override file applied only when set.

14. **Same port for dev and self-host.** Both serve `http://localhost:3000`, so one `.env` (and one `SINTR_URL`) works for either; they cannot run at the same time.

15. **`.env` is generated by POSIX sh.** Self-hosting needs Docker and `make`, not Node.

16. **Versions held back.** TypeScript 5.9 and ESLint 9, because typescript-eslint and the Next lint plugin do not support TypeScript 7 or ESLint 10 yet. Next.js stays on 15 as the brief asks.

17. **English only for now.** The app copy is English; i18n (the site has eight languages) comes later. The person's own words are stored and shown as written, in any language.

## F1 capture

18. **Where the assistant's key lives, and how it is encrypted.** In `agent_settings.api_key`, one row per person, next to the provider, base URL and model (those three in the clear: they name a service, not the person). The key is sealed exactly like ledger content: AES-256-GCM with the person's own data key, bound to `agent_settings.api_key` and the person's id as associated data, so a dump shows an envelope and a key copied to another account fails to open. The settings screen gets `agentSettings.get()`, which reduces the key to its last four characters (and only for keys of 16 characters or more); the key itself comes out only through `credentials()`, on the server, for the call to the provider. It is never sent to the browser, never logged, and saving or removing it is an audit event without the key. A saved key belongs to the provider and address it was saved for: changing either removes it (in the repository, whoever calls it), so it is never sent to another service. A test writes a key and scans the stored row and a text dump of the database for it, and the end-to-end suite checks the page and its data.

19. **Keys and base URLs are always passed to the provider explicitly.** The Anthropic and Google providers of the AI SDK fall back to `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL` and `GOOGLE_GENERATIVE_AI_API_KEY` when nothing is given, which would spend an operator's key on another person's conversation. sintr always gives both (the default base URLs are written in the code), and a test sets those variables and checks they are not used.

20. **Three provider kinds.** An OpenAI-compatible endpoint (base URL, optional key, model) covers OpenAI, OpenRouter, Ollama, LiteLLM, vLLM and most gateways; Anthropic and Google are named. Self-host may point anywhere over http or https, including a model on the same machine (`host.docker.internal` in the self-host stack). SaaS mode accepts only https to a public host name (a trailing dot does not get past the check) and refuses redirects, so a public host cannot bounce a call to an internal address; resolving names to stop DNS tricks is F4 hardening.

21. **A draft is not a record.** The assistant's tools can only propose: a proposal (`proposals`, payload sealed) waits for the person. Confirming it creates the entry or check-in in the same transaction that marks it saved, and a proposal is decided once. The person's explicit yes is the Confirm button, an edited version saved from the card, or a message that is only an instruction to save ("salva", "pode salvar", "save it"). That message is recognised by a strict pattern in the driver, before the model runs; the model never decides that the person said yes, and "salva, mas muda a intensidade" is not a yes. Check-ins drafted in the conversation follow the same rule, so the tool the brief calls "saving a check-in" proposes one.

22. **"Never invent" is checked in code.** Before a draft is stored, its thoughts, hot thought, alternative thought and emotion names must be found in the person's own messages (forgiving case, spacing and quote styles, at word boundaries), and what is stored is the person's span, not the model's copy. Every number (intensities, believability, check-in scales, sleep) must be one the person wrote, in digits or as a small number word (words that are also articles, such as "um", "uma" and "dos", do not count). This stops invented numbers, not misplaced ones: a number written anywhere in the conversation passes for any field, and tying each number to its field is left for later. A time the model writes without an offset is read where the person is, and a bare date is refused, since its time would be invented. A refused draft goes back to the model with the reason, and nothing is kept. The situation and the evidence are allowed to be condensed, so they are not checked word for word; the prompt asks for fidelity there.

23. **The crisis protocol does not depend on a model.** Every message is screened by fixed patterns (Portuguese, English, Spanish) before any model call, after folding case, accents and curly apostrophes. A match stops the diary with a fixed, warm message in the person's language that names CVV 188 and SAMU 192, and the help lines open on screen; this works even with no provider set up. The patterns are sensitive to self-harm and narrow on violence (stated future intent only), because idioms ("morrer de vergonha", "minha mãe vai me matar") and anger told in the past are things people record (an idiom is removed without what follows it, so "morrendo de vontade de me matar" still stops); the model is told to call `signal_crisis` for anything else it notices. From then on that conversation stays paused: the model gets crisis-only instructions and no tools, its failure falls back to the fixed message, and the person can start a new conversation when ready. A conversation that opens on a crisis gets no title, so it is not listed under those words.

24. **The server is the record of a conversation.** The browser sends only the new words; the server loads the history, stores the person's message before the model runs (so a failure loses nothing) and the reply after. A reply that fails (a provider error, not a refused tool call the model can recover from) is not stored, and drafts made during it are withdrawn; a reply that stopped the diary is always stored. Only a new message can say "salva": retrying a failed reply does not. Messages are stored as their UI parts in JSON (`{ v: 1, parts }`) inside the sealed `messages.content`; plain-text rows read as one text part. The model sees the last 40 messages, with each draft's current decision written into its tool result.

25. **What reaches the provider.** The conversation's messages and, when the model asks with `recent_context`, a summary of the last seven days: dates, entry titles (or the first 120 characters of the situation), emotions with intensities, and check-in scales. Nothing else from the diary. Calls run with the AI SDK's telemetry off, and its console defaults (errors written whole by `streamText`, warnings through `process.emitWarning`) are replaced by the redacting logger.

26. **Corrections keep the original.** `entries.correct` and `checkins.correct` update the record and write a `corrections` row with the names of the changed fields (clear) and what they held before plus an optional note (sealed). A change that only fills empty fields reads as completing the record, the pack's "completed with". Fields equal to what is stored are not part of a change; the time field holds minutes only, so a time left as shown is not a change, and line endings are normalised, so a browser's CRLF is not either. A draft edited on its card is laid over the stored draft, so what the person left alone keeps the drafted value.

27. **Conversation retention.** `agent_settings.conversation_retention_days`: empty keeps conversations until the person deletes them (the default); 30, 90 or 365 days after the last message are offered. The worker purges hourly by date, reading no content; drafts go with their conversation, entries and check-ins saved from it stay.

28. **An offline assistant for tests.** `SINTR_FAKE_AGENT=1` replaces the provider call with a scripted model (`@sintr/agent/testing`), so `make test` never reaches a real model or uses a key. A provider must still be saved, the app says on screen that replies are scripted, and saas mode refuses the flag. The unit tests use the same scripted model with explicit scripts.

29. **Plain text from the model.** Replies are rendered as text, not Markdown, and em and en dashes in the model's text are rewritten as it streams (the person's words in drafts are left alone).

30. **AI SDK 7.** The current major at the time of writing; its v7 names are used (`instructions`, `toUIMessageStream`, `onEnd`, `isStepCount`). Data API routes check the `Origin` header on top of SameSite=Lax cookies.

## F2 report

31. **A report is structured JSON, not Markdown.** The pack's report is a Markdown file the agent writes and `report_pdf.py` reads leniently. In the product the model fills one tool (`write_report`) with the prose of the six sections and the choice of moments, and sintr stores the result as JSON (`{ v: 1, ... }`, sealed in `reports.content`, like messages in F1). Nothing has to guess what a model meant, the person edits it as a page rather than as a file format, and the PDF and the app read the same structure.

32. **Moments are copies of entries.** The model chooses which entries become moments and may condense what happened and what the person did; the thoughts, the strongest thought, the emotions and intensities, the evidence, the alternative thought and its believability, and the re-rate are copied from the entry when the report is prepared. The check-in notes are copied from the check-ins. The person may rewrite the prose and remove items, never a copied field (`editReport` refuses it); to change those words they change the entry, and the check then says the moment no longer matches it. Numbers are never typed: the averages, the grid and the chart are computed from the check-ins.

33. **The quote check marks instead of trusting.** Every quoted span in the prose is looked up in the diary word for word (case, spacing and quote styles forgiven, at word boundaries), in the entries and check-in notes of the four weeks up to the end of the period and in the therapy notes. The model gets a refused draft back with the reasons (also causes, clinical labels, undated observations and entries outside the period), twice at most; a draft still wrong is kept and marked, so the person sees it before approving. A quote that is not found keeps its marks but never gets the peach highlighter, in the app or the PDF, so the page's promise ("highlighted words are the person's exact words") stays true even for words the person typed in themselves.

34. **The period follows the pack, with three product rules.** A report is for a session and covers the days since the previous report ended, up to `report_lead` before the session; the first covers the 7 days before; without a session it is the calendar week, as far as it has gone (Monday, or where the previous report ended, to the moment it is prepared; preparing it again takes it further, never past Sunday), so no report claims days that have not happened. In addition: after a pause longer than four weeks, a period reaches back four weeks, not to the last report; a one-off date (`therapy_settings.next_session_at`) replaces the weekly session nearest to it (within half a week) and the weekly schedule resumes after it; and nothing is prepared for a session that already started (a worker that was down skips it, and the next report starts where the last one ended, so nothing is lost).

35. **A moved session moves the draft.** If the latest report is an untouched draft (`edited_at` empty) for a session that is no longer in the schedule, or that has not happened yet, the scheduler prepares that same report again for the new session (same start, new end, a revision kept) instead of starting a second one. A draft the person changed is never rewritten by the scheduler.

36. **Scheduling is a reconciler, not timers.** The worker runs `prepare-reports` every minute: for everyone with a session it asks the planner (`planScheduledReport`) what is due now, from the schedule as it is now. A changed setting or a restart needs no rescheduling, and two unique keys, `(user_id, period_end)` and `(user_id, session_at)` for session reports, keep a retried tick, a second worker or two tabs from keeping two reports for the same period or session. The worker prepares only for people whose latest consent to process their health data is granted and current, the same gate every page applies. A preparation abandoned by the person (a reload during "Prepare it now") keeps nothing. The scheduler takes a clock, so the tests move time by hand. "Prepare it now" runs in the request instead, because the person is waiting for it; it covers what exists so far, and the scheduler later brings that draft up to the preparation time if it is still untouched.

37. **Two yeses: approve, then send.** Approving freezes the numbers into the content and prints the final PDF (no draft mark), which is stored; it sends nothing. Sending is a second, explicit yes on that report that names the recipient: the browser sends back the address the person saw, and the server refuses if the settings changed since. The consent (`report_send`, versioned, naming the report and the recipient) and an audit event are recorded and committed first, so they stay on record whatever follows; then the email is sent with the report row locked, and the report is marked sent (recipient and time) only after the transport accepted it. A second send of the same report waits for the lock and then finds it sent, so the therapist never gets it twice; a failed send is audited and leaves it approved. Approving is refused if the draft changed (an edit, a new preparation) while its PDF was printing, so what is approved is what the person read. Any change to the words makes it a draft again; a sent report is final, and its PDF stays available. `require_approval` stays a constant, not a switch.

38. **Email is one interface and SMTP from the environment.** `EmailTransport` has four implementations: SMTP (nodemailer, `SINTR_SMTP_*` and `SINTR_EMAIL_FROM`), an outbox directory for the end-to-end tests, an in-memory fake for unit tests, and off (the default). A managed provider can be a fifth later. Transports never log and refuse a second recipient or a header in the subject. Email carries no diary content except the PDF the person approved: the notice to the person is a link and a sentence, sent only when they opted in (`report_notice_email`) and to a verified address.

39. **Password reset and email confirmation open with email.** The Better Auth routes F0 kept closed (`/request-password-reset`, `/reset-password`, `/send-verification-email`, `/verify-email`) are enabled only when a transport is available, and stay closed otherwise. A confirmation link is sent at sign-up but not required to sign in: a self-hosted diary must not lock its owner out over a mail setting. These emails are not awaited and a failed send is logged as a code, so neither the answer nor the time it takes tells who has an account. Sign-up still does (F0, decision 7); closing that needs `requireEmailVerification`, which changes sign-up and is left for F4.

40. **The PDF is HTML printed by Chromium, embedded and offline.** `reportDocument` builds one self-contained page (the sintr design system, the fonts and the window light inline, no script) and `renderPdf` prints it with playwright-core, JavaScript off and every request refused; there is nothing to fetch and nothing to run. The light is the app's own `WindowLight`, rendered once to a JPEG by `make report-assets` (blur and blend modes look different in each PDF viewer). The fonts and the light are embedded in a generated module, so the web app (which bundles `@sintr/core`) reads no files at run time; a test fails if they drift from `packages/ui/fonts`. The Docker image installs Alpine's Chromium and points `SINTR_CHROMIUM_PATH` at it; development and tests use Playwright's, which `make setup` installs. playwright-core is pinned to the same version as `@playwright/test`, so both use the one browser CI caches by that version. Chromium runs without its own sandbox, as Playwright does by default and as an unprivileged container requires; the page it prints is our own escaped HTML, offline and without script. A browser is started per print, at most two at a time per web process; a draft's preview is printed on demand, an approved report's PDF is read from storage.

41. **The report's language is the person's choice.** `profiles.language` (English, Portuguese or Spanish, chosen in Therapy) sets the report's headings and the language the assistant writes in; the person's own words are never translated. The app's copy, dates included, stays English (decision 17).

42. **Without an assistant, sintr prepares what it can.** With no provider, a provider that fails, or a model that answers without the tool, the draft holds the moments copied from the strongest entries, the check-in notes and the person's own topics, and says why the prose is empty. Nothing is made up to fill it.

## F3 connect your agent

43. **MCP is a stateless route of the web app.** `/mcp` is Streamable HTTP in stateless mode with JSON answers: every POST carries its key, runs a fresh server inside that person's scope, and leaves nothing behind (no session id to store, no event stream to hold open, `GET` and `DELETE` answer 405). One process model, the same as every other route, and nothing to clean up or leak. It sits outside `/api` (where the session cookie and the origin check rule) and outside the page middleware (CSP nonces), because the key, not a cookie, is its credential. Its limits (calls per key, each message of a batch counted, wrong keys per address, body size) are counted in memory per web process; a second process only loosens them. Only wrong keys are throttled by address, after the lookup: ChatGPT and Claude call from shared addresses, so one person's stale key must not lock out everyone else's working one.

44. **The key is the only credential, as a header or inside the address.** `Authorization: Bearer` is the normal path. ChatGPT cannot send a key of its own, and Claude's request headers are in beta for some organisations, so `/mcp/<key>` is accepted too; the address is then a secret, the route is logged as `/mcp` only, Caddy keeps no access log, and the Connect screen says so. OAuth is the standard way for remote clients and would remove the key from the address, but it is a whole authorization server (registration, consent, refresh); it is left for later. A browser on another origin is refused and no CORS headers are sent, so no web page can use a key; cookies are never read.

45. **Three kinds of access over the per-data-type scopes.** The scopes from F0 stay per data type; the app offers three sets of them ("Read and save", "Save only", "Read only", in `API_TOKEN_ACCESS`), holding only the scopes the tools use. A key lists only the tools its scopes allow, and every call checks again. "Save only" exists for a person who wants their assistant to record without ever reading the diary back.

46. **Over MCP, a save is a record, not a draft.** In Talk a draft waits for the Confirm button or a "salva" that sintr recognises itself (decision 21). Over MCP the conversation belongs to the person's assistant and sintr cannot see their yes; making them open sintr to confirm each draft would defeat the point of staying in their assistant. So the instructions require showing the draft and saving only after the yes, `save_entry` and `save_checkin` require `personConfirmed: true`, the record is held to the same checks as Talk's drafts, and the person can correct it in the app, which keeps what it said before (decision 26). The audit log records each save with the key's id.

47. **The capture rules are imported, not copied.** The checks that keep a draft in the person's words, the crisis screen and its fixed messages live in `@sintr/agent` since F1. The MCP server imports them from a light entry, `@sintr/agent/rules`, which loads no AI SDK at run time; scoping, sealing and the domain validation come from `@sintr/core`. Moving the rules into core was considered: they are capture rules, both shells now use the same functions, and a move would only rename them.

48. **The person's words travel with the save and are dropped.** The verbatim checks need the person's own messages, which only the assistant has, so it passes them in `personWords` (at most 40, each at most 20,000 characters, 1 MB per request). sintr checks the draft against them, stores the person's exact spans, and keeps nothing else of them. An assistant could pass words the person never said; the instructions forbid it, and the checks still stop paraphrase and invented numbers coming from the model's own copy.

49. **The crisis protocol over MCP.** sintr cannot interrupt another assistant's conversation. The instructions put the protocol first (stop the diary, warmth, CVV 188, SAMU 192, the local emergency number, someone they trust), and every save screens the person's words and the draft with the patterns of decision 23: on a match nothing is saved and the answer carries `"crisis": true`, the fixed message in the person's language, the lines, and the instruction to stop. It is logged as a code.

50. **Reads are small, and the report stays in the app.** `recent_context` is F1's summary (decision 25) with ids, at most 14 days; `read_entry` opens one entry; `therapy_overview` leaves out the therapist's name and address, which the assistant does not need; `prepare_report` returns the digest of the next report's period (computed exactly as the report would be, at most 40 entries) and the report's status, and changes nothing: preparing a draft would be a write under a read key and would spend the person's in-app provider. Nothing in MCP can approve or send a report.

51. **The stdio bridge forwards; it is not a second server.** Local clients run `sintr-mcp.mjs`, which forwards stdio to `/mcp` with the key from `SINTR_URL` and `SINTR_TOKEN` (or `~/.config/sintr/mcp.json`). It has no database access, so the HTTP endpoint stays the one place keys, scopes and checks are enforced. It is bundled into one file and served by the app at `/sintr-mcp.mjs`, so a person gets it from their own sintr; it refuses to send the key over plain http to another machine unless told to.

52. **"Connected" comes from the key itself.** `last_used_at` is updated on every authenticated call, and the name a client gives at `initialize` (`clientInfo.name`, letters, digits and a few marks, at most 60) is kept in `api_tokens.last_client`. The Connect screen turns "Waiting for your assistant" into "Connected" by refreshing while a new key waits, and each key says when it last talked to sintr and from which client. The name is the client's own claim, shown as text, never trusted for anything.

53. **Connect is a screen of its own.** It is in the navigation next to Settings, written for someone who has never heard of MCP: one sentence first, one button for a key (name and access optional), the key shown once, each assistant's steps with the address and key filled in, the live line, and the technical detail behind a closed disclosure. Settings lists the same keys. Each client's commands, files and menus were checked against its documentation on 2026-10-18 (`docs/MCP.md` lists the sources); what could not be checked is said on the screen instead of guessed. Keys made without a name are numbered ("My assistant 2").

## F4 the therapist

54. **One account kind; a practice is opened from inside.** There is no therapist sign-up. Any account can open one practice (a unique index on `practices.user_id`) from Settings or `/practice`, or on the way while accepting a person's invite. Someone who never opens one sees nothing new except Sharing, the person's own side; the Practice group appears in the navigation only once a practice exists. The professional's own diary is untouched by it.

55. **The link is the unit of trust, and the database holds its rules.** A link joins one person and one practice and is `pending` (a practice accepted the person's invite, the person has not confirmed), `active` or `ended`. A check refuses `active` without the person's consent and both acceptances; another refuses an ended link that still holds a key or a name; a partial unique index keeps one open link per person and practice. The ended row stays, with ids and dates only, so both audit logs keep pointing at something.

56. **Double opt-in in both directions, and the person's yes always names the practice.** A practice's invite is the practice's yes; the person sees the professional's name and details, then accepts with the consent (`practice_link`, versioned, recording the practice as shown). A person's invite to their therapist cannot carry that consent, because the person does not yet know who will accept it: the professional accepts from their practice (which holds a seat), and the person then confirms that practice by name, with the consent. A code that reaches the wrong hands can never receive anything without the person's later yes to that exact practice.

57. **Invite codes.** Twelve characters of Crockford's base32 (60 bits), shown as `XXXX-XXXX-XXXX` to be read aloud or typed, and the link `/join/<code>`. Typing forgives case, spaces, dashes and the letters that look like digits. Codes are looked up by an HMAC keyed from the master key (HKDF), so a dump alone cannot be searched by trying every code; the code itself is kept sealed for its creator to copy again. Seven days, one use, revocable. Unknown, expired, revoked and used codes get the same page, and lookups are limited per address (30 every 10 minutes, in memory). `/join` shows who is inviting to anyone holding the code, signed in or not: the name is what makes the link trustworthy, and the holder is who it was sent to.

58. **What travels through a link is sealed with the link's own key, and ending the link destroys it.** Each link gets a data key wrapped by the master key and bound to the link's id (`links.wrapped_key`, key material like `user_keys`). The name the person chose and every shared report (page and PDF) are sealed with it. Ending a link deletes the copies and sets the key and the name to null, which the database requires of an ended link: even a copy that survived somewhere in the live database could not be opened any more. A database backup taken before still holds the key; that is said in PRIVACY.

59. **Two openings across accounts, both of words written for that audience.** The practice's names are sealed with the professional's own key and opened for the people holding its invite or linked to it; the name a person chose for their invite is sealed with their key and opened for the professional holding the code. Nothing else of one account is ever opened for another, and both openings live in one module (`repositories/links.ts`).

60. **A shared report is a copy of what was approved, never a view into the diary.** Sharing copies the approved content (its numbers frozen at approval, and which quotes were found word for word, so the highlighter means the same thing) and the approved PDF into `shared_reports`. The practice side has no query that reaches entries, check-ins, conversations, drafts or any report that was not shared, and none that runs through a link that is not active. Each share needs a `report_share` consent naming the report and the link; composite keys make the database refuse a share whose link, report or consent belongs to another person. A shared report's words are final, as a sent one's are.

61. **"Ask me each time" by default; "send what I approve" keeps the per-report yes.** With the second, approving is the yes for that report: the approve button names the practices ("Approve and share with Dr. ..."), the browser sends back the links it named, and the server approves nothing if they changed since. A consent is recorded for each report and practice either way. With the first, the report page offers one explicit yes per practice after approval, like an email send.

62. **Ending is one action, from either side, at once.** The person's "Stop sharing" and the professional's "Disconnect" end the link the same way: copies deleted, the link's key and name destroyed, notices about the link removed, the other side told. When the person ends an active link, a withdrawal (`granted = false`) is added to their consent log. The professional's notice says a patient ended their link, without the name: that name was the person's, given under the consent just withdrawn. A PDF already downloaded is outside sintr; the screen says so before the person stops.

63. **Audited in both accounts.** Events across a link are written to the audit log of each account concerned (the person's and the professional's), so each log is complete on its own: invites made, revoked and accepted, links activated, declined, ended and changed, consents, shares made, read and downloaded. The person also sees, on each shared report, when it was first opened.

64. **Seats, structurally, without payments.** A practice has a plan label and a seat count. A seat is taken by an active link and held by a link waiting for the person's confirmation or a practice invite not yet accepted; every seat check runs with the practice row locked. Seats come from the installation (`SINTR_PRACTICE_SEATS`, unlimited on a self-host, none on the hosted offer) until a grant for that practice: `make practice-plan` (also bundled into the image as `worker/practice-plan.mjs`) calls `setPracticePlan`, audited in the professional's log. A payment provider will be a third `seat_source` whose webhook calls the same function. Lowering seats never ends a link; it only refuses the next acceptance.

65. **Notices carry no words.** `notifications` holds a kind and ids; the sentence is written when it is shown, with the names the reader may see at that moment. The person learns in the app when a practice accepted their invite or ended a link; the professional learns of new links and new reports. A small dot beside Sharing or Practice says there is something new, cleared once the notices were on screen. The professional may opt in to an email per new report (`practices.notify_email`, to a confirmed address): the worker sends a link and a count, never a name or a word, and claims each report before sending so it is told at most once.

66. **The dashboard centralises access, not analysis.** It counts active patients and seats, lists pending invites, patients and received reports by recency, and opens a report in place beside the list (`/practice?report=`), set with the same paper as the person's own page. Report links are never prefetched, because opening one is a recorded reading. There is nothing computed across patients.

67. **A neutral label.** A person who chooses no name is "Patient N", N being the practice's own count, assigned with the practice row locked. The person is told what the practice sees ("They see you as Patient 3, a neutral label") and can change it.

68. **The crisis lines stay with the person.** Every page of the person's side and the invite page keep CVV 188 and SAMU 192 in the footer. The practice pages replace them with a note for the professional: reports arrive when a person approves them, never in real time, and sintr is not a monitoring tool or a crisis channel.
